# ADR-0004: ngkit ships no HTTP client; applications use Angular's `HttpClient`

**Status:** accepted (2026-09-23, amended 2026-10-24) · **Scope:** every ngkit entry point, existing and future

## Decision

The basic HTTP client is Angular's `HttpClient`. ngkit ships no HTTP entry point.

- OpenAPI 3.1 plus the standards referenced by the API document are the sole authority for paths, methods, parameter serialization, headers, media types, request/response schemas, status codes, security and errors. ngkit must not create a parallel client schema or silently change the documented wire behavior.
- An operation client owns one method per OpenAPI operation. Its method name, input/output types and serialization follow the document, preferably through generation. A hand-written client follows the same rule and is tested against the document.
- Framework implementation is unobservable. Do not mention or detect any backend framework or server library in ngkit code.
- Do not add resource models, request/response base types, pagination envelopes, health models, header-name constants, error taxonomies or domain adapters. Generated/application code owns document schemas.
- Do not add retries, caching, deduplication, polling, redirects, authentication, tracing, logging, metrics, idempotency, concurrency or error mapping to a transport wrapper. Use Angular interceptors or the application's observability layer when the OpenAPI/HTTP contract calls for them.
- **RFC 9457 is the one error shape ngkit types**, as a published standard (ADR-0001 principle 1): `ng/core` types its five members and recognizes a problem by the `application/problem+json` media type, with no error class or interceptor; `HttpErrorResponse` stays unchanged. No extension member has a meaning in `core`; only `ng/crud` reads one, `errors`, for form mapping.

## Consequences

- **Generic CRUD client.** Not in `ng`. A generic `RestResource<T>` encodes a backend convention (list envelope, ID type, PUT vs PATCH, nested routes). That is the same adapter dialect removed with `http/crud`. Prefer generated clients; otherwise an app may keep a ~15-line generic base of its own that implements the screen's data-source contract. Only a published, versioned convention shared by several backends would justify a separately named adapter package.
- Applications own their base URLs, interceptors and error policy; [the HTTP guide](../guides/http.md) shows the pattern.
- `ng/crud`'s shape-detected `ProblemDetails` is replaced by the `core` type ([E14](../specs/epics/E14-problem-client/index.md)).
- Telemetry is deferred work ([F12.1](../specs/epics/E12-on-demand-features/index.md)), not part of this decision.

## Alternatives considered

The last version of `OpenApiHttpService` was `inject(HttpClient)` plus `${baseUrl}${path}`. That did not justify a public entry point:

- **One global base URL.** `RN_FORGE_HTTP_CONFIG` held one `baseUrl`, but apps call several backends. A singleton injected into every service makes that worse, and generalizing it (per-service tokens, overridable `baseUrl`) just re-creates what an app-owned `InjectionToken` already does.
- **The name promises behaviour it doesn't have.** Nothing in the class read an OpenAPI document; any HTTP API client would use it the same way.
- **Composition costs the same.** Two `inject()` field initializers replace `extends`, with no constructor coupling.
- **No boilerplate saved.** The largest real saving is a generated client, which does not need ngkit either.

Do not rename it, generalize it or add a second "basic" client.

For problem responses (E14), two further options were rejected:

- **An `ApiError` class.** With no extension member given a meaning, it would carry the same fields as `HttpErrorResponse` under a new name, and every `instanceof HttpErrorResponse` check, interceptor and `ng-bootstrap` reader would have to learn it.
- **A rethrowing interceptor** that replaces `HttpErrorResponse` with a parsed problem. It changes Angular's error type for the whole application to save one `problemOf` call at the screen that needs it.

## Background

Accepted 2026-09-23 with "problem types" on the list of shapes ngkit must not add. That ban was aimed at a parallel client schema invented by ngkit. On 2026-10-24 (owner request, 2026-10-21; [E14](../specs/epics/E14-problem-client/index.md)) the decision was amended to type the RFC 9457 members, because a published standard falls under ADR-0001 principle 1 and an application rewrite reading problems from its backend needed one shared definition.
