# ADR-0006: The SPA is an OIDC client; the identity provider signs users in and issues tokens

**Status:** proposed (2026-09-23) · **Scope:** `@rn-forge/ng/auth` and `@rn-forge/ng-bootstrap/auth`

Proposed, not accepted: the roles below are decided, but no code exists and whether the SPA is a browser client or fronted by a backend-for-frontend is open ([S5.1.1](../specs/epics/E5-oidc-client-auth/F5.1-client-model.md)).

## Decision

- **The identity provider signs users in.** An OAuth 2.0 / OIDC authorization server (Entra ID, Keycloak, Auth0, …). SSO and SAML federation happen at the identity provider, not in each API.
- **The API is a resource server.** It verifies bearer JWTs (RFC 6750, RFC 9068) through OIDC discovery and JWKS and answers 401 with a challenge / 403 without one.
- **The SPA is an OIDC client.** Authorization Code + PKCE (RFC 7636; RFC 9700 OAuth 2.0 Security BCP; OAuth 2.1). No implicit flow, no password grant.
- **Basic auth** stays local-development and simple-internal only. The SPA does not offer it.

## Consequences

`@rn-forge/ng/auth` is replaced, not fixed, because the current custom layer gets these wrong:

- login is a custom `POST` returning snake_case `access_token`/`refresh_token`, not a standard grant;
- the JWT is kept in `localStorage`, readable by any XSS;
- `UserProfile` is a Django user (`is_staff`, `is_superuser`, `groups[].permissions`) decoded from a custom `profile` claim;
- the interceptor attaches the token to every URL except an ignore-list, so it can leak to other origins;
- 401/403 are checked on successful `HttpResponse` events, which Angular never delivers, and **403 sends the user to login**, contradicting HTTP's meaning of 403 (authenticated but not allowed) and causing redirect loops.

## Influences

[E5](../specs/epics/E5-oidc-client-auth/index.md).

## Alternatives considered

- **The current custom login `POST` with tokens in `localStorage`.** Non-standard grant, XSS-readable token, redirect loops on 403 (above).
- **Implicit flow.** Deprecated by the OAuth 2.0 Security BCP.
- **Password grant.** The SPA would handle user credentials directly; removed in OAuth 2.1.
