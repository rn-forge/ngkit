# ADR-0006: The browser holds a backend session, never a token; the backend runs every login protocol

**Status:** proposed (2026-10-16) · **Scope:** `@rn-forge/ng/auth` and `@rn-forge/ng-bootstrap/auth`

Proposed until [S5.1.1](../specs/epics/E5-session-client-auth/F5.1-client-model.md) accepts it.

## Decision

- **The backend is the OAuth client and SAML service provider** (the backend-for-frontend model). It runs OIDC, SAML, social, local-password and development logins, and keeps the result in a server-side session tied to an `HttpOnly` cookie.
- **The SPA is a client of that session, not an OAuth client.** It starts logins by full-page navigation, reads identity and permissions from the backend's session resource, and sends the cookie plus a CSRF header. It never stores a token or sends an `Authorization` header.
- **The SPA mirrors authorization; the server decides it.** Permission keys from the session show or hide features; the server rechecks every request. A `401` means sign in; a `403` means signed in but not allowed and never signs the user out.
- **SPA and API share one origin.**

## Consequences

- No OIDC client library, token storage or refresh logic in ngkit; the client is `HttpClient`, the router and Angular's XSRF support.
- Revocation and logout take effect on the server immediately.
- SAML and social login need no broker.
- Deployments need a same-origin proxy, and the client must handle CSRF and guard against a login loop when the cookie is never stored.
- `@rn-forge/ng/auth` is replaced, not fixed (the reasons are in [E5](../specs/epics/E5-session-client-auth/index.md#why-replace-not-fix)).

## Influences

[E5](../specs/epics/E5-session-client-auth/index.md) and its [wire contract](../specs/epics/E5-session-client-auth/design.md).

## Alternatives considered

- **The SPA as a browser OIDC client** (PKCE, tokens in memory, rotating refresh tokens). Script in the page can still acquire new tokens; revocation waits for expiry; SAML and social login always need a broker. Kept as a situational profile for a SPA with no backend ([F5.5](../specs/epics/E5-session-client-auth/F5.5-situational-client-extensions.md)).
- **Token-mediating backend.** The backend runs the login and hands the SPA an access token, which is still within reach of script.
- **The current custom login `POST` with tokens in `localStorage`.** Non-standard grant, XSS-readable token, redirect loops on `403`.
- **Implicit flow and password grant.** Deprecated by the OAuth 2.0 Security BCP and removed in OAuth 2.1.

## Background

Proposed on 2026-09-23 as "the SPA is an OIDC client; the identity provider signs users in and issues tokens", with the browser-client-or-BFF choice left open. Rewritten on 2026-10-16, when the owner redefined E5 around the backend session: every application this client targets has a backend, and the IETF "OAuth 2.0 for Browser-Based Applications" draft ranks the backend-for-frontend first for that case.
