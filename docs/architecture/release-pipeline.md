# Release pipeline

How ngkit builds, versions, packs and publishes its libraries. The choices
behind it are [ADR-0003](../adr/ADR-0003.md); the procedure is
[Releasing](../runbooks/releasing.md).

The pipeline is generated by kiln from `.rn-forge/kiln/config.toml`: `ci.yml`
calls the reusable workflows `_release.yml`, `_docs.yml`, `_smoke.yml`,
`_sonar.yml` and `_verify-release.yml`, and every step runs a `task ci:*` task
from `tasks/ci.yml`. None of these files is edited here; a change goes through
the config (`.rn-forge/kiln/standard.md` states the rules).

## Version and release

The version is bumped in a pull request with `task version -- <bump>` (`patch`,
`minor`, `major` or `x.y.z`). It runs `nx release version` and
`nx release changelog` without committing, tagging or staging, so the pull
request carries the new `libs/*/package.json` versions and the `CHANGELOG.md`
section. `nx.json#release.version.preVersionCommand` builds the publishable
projects during that step; nothing downstream consumes the `dist/` it leaves,
because `dist/` is gitignored.

The release is the `release` job in `ci.yml`, which calls `_release.yml`. It
runs only on a push to `main`, after `checks-ok`, and never commits. In order:

1. `ci:release:state` reads the version from the publishable projects and sets
   the mode (below), the tag `v<version>`, whether this is the first release,
   and the npm dist-tag (`latest`, or the prerelease id for a `x.y.z-id.n`
   version).
1. `ci:release:tag` tags `HEAD` (mode `new` only).
1. `ci:release:verify` rebuilds `dist/` from the tagged source, with task
   dependencies, then runs `pack`, `verify-dist` and `verify-consumer` on
   every `publishable` project, and fails when no tarball was written.
1. `ci:release:push` pushes the tag and nothing else (mode `new` only). The push
   runs as the release GitHub App, a bypass actor on the tag ruleset;
   `GITHUB_TOKEN` cannot bypass it.
1. `ci:release:github` creates the GitHub Release for the tag as a draft, with
   the tarballs and the `CHANGELOG.md` section as notes.
1. `ci:release:publish` runs
   `nx release publish --tag=<dist-tag> --excludeTaskDependencies`, so it uses
   the `dist/` the verify step built. It is a dry run while npm is disabled.
1. `ci:release:finalize` publishes the draft, so a published release is a
   finished one.
1. `ci:release:latest` moves the rolling `latest` release to the tag.

**Modes.** A version counts as shipped when its GitHub Release is published (not
a draft).

| Tag `v<version>` | Published release for it | Mode | Run does |
| -- | -- | -- | -- |
| absent | n/a | `new` | every step above |
| at `HEAD` | no | `resume` | every step except tag and push: rebuilds from the tag, replaces any draft, publishes, updates `latest` |
| any | yes | `released` | nothing, apart from the notice; `verify-release` is skipped |

A tag that exists but is not at `HEAD` fails the run: a failed release resumes
only from its own commit. A failure before the push leaves nothing public.

**Rolling `latest`.** The step is idempotent: it is skipped when the remote
`latest` tag already points at this tag's commit and the `latest` release has
the same asset names as the tag's release. Otherwise it deletes and recreates
`latest` with the tarballs.

**`verify-release`.** After `release`, when it published a tag, the
`verify-release` job downloads the tarballs from the published GitHub Release
and runs `verify-consumer` on them (`task ci:verify-release`), so the install is
checked against what consumers download rather than what the runner built.

The current version comes from git tags (`currentVersionResolver: "git-tag"`,
falling back to `disk`, in each library's `project.json`). Bumps are chosen by
the person running `task version`, not derived from commits
([ADR-0003](../adr/ADR-0003.md)).

Only `main` releases; kiln's generated release has no other branch
([ADR-0003](../adr/ADR-0003.md#background)).

## Pushing the release

`nx.json#release.changelog.workspaceChangelog.createRelease` is `false`, so
`nx release` writes versions and `CHANGELOG.md` locally and creates no GitHub
Release. The release job pushes the tag itself (`ci:release:push`, the tag and
nothing else) only after `pack`, `verify-dist` and `verify-consumer` pass on the
rebuilt `dist/`, so a failed check leaves nothing public. It then creates the
GitHub Release with `gh release create`, as a draft, which uploads the tarballs
and uses the `CHANGELOG.md` section as the notes.

## CI

`ci.yml` runs on a push to `main`, on a pull request to `main` and by
`workflow_dispatch`, whose only input is `use-nx-cloud`. There is no
`release/**` trigger. The jobs:

- **`validate`**: runs `task setup`, then `task ci:validate`: Markdown, TOML and
  YAML formatting, `kiln doctor` (`--full` on a push to `main` or a dispatch),
  workflow security (zizmor and actionlint), the check that members depend on
  each other by `workspace:^` or `workspace:~`, and the docs build. It runs
  before everything else.
- **`dependency-review`** (pull requests, after `validate`) and
  **`secret-scan`** (gitleaks over the full history, skipped for fork pull
  requests); a skipped job passes.
- **`test-cloud`**: when the repository variable `USE_NX_CLOUD` is `true`, or a
  dispatch checks `use-nx-cloud`, distributes `lint`, `test`, `build` and
  `e2e-ci` across Nx Cloud agents using the `linux-medium` launch template
  (`.nx/workflows/agents.yaml`); the agent count comes from the repository
  variable `NX_CLOUD_AGENTS` (optional, default 3).
- **`test-local`**: otherwise, runs `lint test build e2e` on one runner, with no
  Nx Cloud dependency. Playwright browsers install only when a project has an
  `e2e` target.
- **`smoke`**: after either path succeeds, `_smoke.yml` runs `task ci:smoke`
  (`nx run-many -t pack verify-dist verify-consumer`, every project that
  defines each target) and uploads the tarballs as a `package-tarballs`
  artifact.
- **`sonar`**: skipped on Dependabot and fork pull requests (no `SONAR_TOKEN`).
  `_sonar.yml` runs `task test:coverage`, finds the lcov reports under
  `coverage/` (it fails when there are none) and scans them; it waits for the
  quality gate.
- **`checks-ok`**: gathers `validate`, `dependency-review`, `test-cloud`,
  `test-local`, `smoke`, `sonar` and `secret-scan`. It fails when any failed
  or was cancelled; skipped jobs pass.
- **`release`**, **`verify-release`** and **`docs`**: described under
  [Version and release](#version-and-release) and [Docs site](#docs-site);
  `release` and `docs` wait for `checks-ok`.
- **`ci-ok`**: the one check branch protection requires. It gathers `checks-ok`,
  `release`, `verify-release` and `docs`, so a failed release or deploy fails
  it too. Skipped jobs pass.

There is no `template` job. `ci.yml` is one toggle between distributed
(`test-cloud`) and local (`test-local`) execution, not two pipelines.

Playwright e2e uses the atomized `e2e-ci` target (`@nx/playwright/plugin`'s
default `<targetName>-ci`) so Nx Cloud can distribute individual spec files as
separate tasks. Only the cloud path needs it; the local path runs plain `e2e`.

Every job checks out the repository, then uses `.github/actions/setup`, which
installs pnpm (version from `package.json#packageManager`) and Node (version
from `.nvmrc`), installs uv, and installs dependencies. The Nx Cloud agent image
(`ubuntu22.04-node24.14-v1`, in `.nx/workflows/agents.yaml`) names its own Node
version, which must be kept in step with `.nvmrc` (24); the agents install uv in
an init step when the repository commits a `uv.lock`.

## Docs site

The `docs` job in `ci.yml` calls `_docs.yml`, which publishes one GitHub Pages
site on every push to `main` after `checks-ok`, `release` and `verify-release`
have passed or been skipped, so a failing commit never deploys. `deploy-pages`
replaces the whole site, so every deploy builds all of it: `task docs:build`
(MkDocs), then `task ci:docs:site`, which runs
`nx run-many -t compodoc build-storybook` and assembles the result under
`.docs-site/`: the MkDocs site at the root, Compodoc under `api/<project>/` and
Storybook under `storybook/<project>/`. The `pages` concurrency group has
`cancel-in-progress: false`, so a deployment in progress is never cancelled.

The job names no project. Each project declares its own doc targets (`compodoc`,
`build-storybook`) and the assembly reads the projects that declare them. A new
library appears on the site by declaring the targets.

## Publishable tag

A library is released when its `project.json` carries the tag `publishable`.
`nx.json#release.projects` is `["tag:publishable"]` and `preVersionCommand` and
`preVersionCommand` and the generated release steps select `-p tag:publishable`,
so no project list appears in release config or workflows. Adding a library to
the release is tagging it.

## Manifest roots

Each publishable library's `project.json` sets
`release.version.manifestRootsToUpdate` to both `{projectRoot}` and
`{ "path": "dist/{projectRoot}", "preserveLocalDependencyProtocols": false }`.

- `dist/` is gitignored and ng-packagr regenerates it from source on every
  build, so without also bumping the source manifest, `libs/*/package.json` on
  `main` would never reflect the released version.
- `workspace:` references must never leak into a published dist manifest.
  `preserveLocalDependencyProtocols: false` on the dist manifest root is the
  guard; keep it if a genuine `workspace:` dependency is ever added between
  these libraries.

## `patch-package-exports`

The shared script `tools/scripts/patch-package-exports.mjs` takes a project root
and `subpath=target` pairs and adds them to the ng-packagr dist `package.json`'s
`exports` map, which ng-packagr computes from compiled entry points only.
`ng-bootstrap`'s `patch-package-exports` target uses it so deep asset imports
(`@rn-forge/ng-bootstrap/assets/*`) resolve at all; `ng-tailwind`'s uses it to
export `./tokens.css`, `./base.css` and `./tailwind.css` from `assets/`. The
target is a `dependsOn` of each library's `pack` override and is run by
`preVersionCommand` for every publishable project that defines it. It must
execute after every build of the library. Any new library shipping non-TS assets
alongside compiled entry points needs the same pattern.

## Packing

`pack` and `verify-dist` are defined once, in `nx.json#targetDefaults`; each
publishable `project.json` declares them as `"pack": {}` and
`"verify-dist": {}`. `ng-bootstrap` and `ng-tailwind` override only
`"pack": { "dependsOn": ["patch-package-exports"] }`.

- **`pack`** depends on `build`, runs `task ci:dist:resolve` on the dist
  directory, then `npm pack` into `dist/tarballs/`. The task rewrites any
  `workspace:` protocol dependency to the referenced local package's current
  version. The release and the `smoke` job both run `nx pack`, which never
  runs `nx release version`, so without it `ng-bootstrap`'s dist
  `package.json` would carry a literal `"@rn-forge/ng": "workspace:^"` peer
  that an external `npm` or `pnpm install` cannot resolve. It is where the
  caret internal ranges come from.
- **`verify-dist`** depends on `pack` and is never cached. It runs
  `task ci:dist:verify -- dist/<projectRoot>`, which asserts that no
  `workspace:` protocol remains in the manifest's `dependencies`,
  `peerDependencies` or `optionalDependencies`, and that the ng-packagr output
  is complete: `name` and `version` are set, and there is `module` or
  `exports`, and `typings` or `exports`. It runs from both the `smoke` job and
  the release.

## Consumer verification

`tools/scripts/verify-consumer.mjs`, run by the `verify-consumer` target (which
depends on `pack`), installs the packed `@rn-forge/ng` tarball via `file:` into
four throwaway fixtures under `dist/consumer-fixtures/` (outside the pnpm
workspace glob): Angular 22.0.6 and 22.1.7, each with and without `zone.js`
loaded. It smoke-tests every secondary entry point (`.`, `./core`, `./auth`,
`./crud`) plus a `LocalStorageService` round-trip through DI, and asserts the
installed manifest carries no `workspace:` protocol dependency.
`node tools/scripts/verify-consumer.mjs ng-tailwind` (the `ng-tailwind` target)
runs the same Angular matrix with the `@rn-forge/ng-tailwind` tarball, but
builds real applications with `ng build`: a plain one importing `tokens.css`,
and one with `tailwindcss` and `@tailwindcss/postcss` importing the sheets in
the README order. It asserts on the built CSS and JS: the plain build carries
`--rnf-surface-0` and the button's `rnf` layer rules and has no `tailwindcss`
installed; the Tailwind build emits the mapped utilities resolving to
`var(--rnf-*)` and none for the default palette. There is no verdaccio and no
workspace fixture. The script also takes `--only plain|tailwind` and
`--cell <angular>-<zone|zoneless>`; the `ng-tailwind:consumer-fixture` target
uses them (`--only tailwind --cell 22.1-zoneless`) to build the single Tailwind
fixture that `ng-tailwind-e2e` serves for its cascade checks, and the full
matrix is unchanged. It runs in the `smoke` job and the release.

## What a repository declares

The generated CI reads these declarations and names no project. They are ngkit's
own, and a new publishable library must carry them
([adding one](../guides/development.md#adding-a-publishable-library)).

- `.nvmrc`: the Node version `.github/actions/setup` installs.
- `package.json#packageManager`: the pnpm version.
- `nx.json#nxCloudId`: the Nx Cloud workspace.
- `nx.json#release`: `projects` (`["tag:publishable"]`), `version`
  (`preVersionCommand`) and
  `changelog.workspaceChangelog.createRelease: false`.
- `nx.json#targetDefaults` for `pack` and `verify-dist`.
- The `publishable` tag on every released project.
- Targets: `lint`, `test`, `build` and `e2e` (run by `test-cloud` and
  `test-local`; `e2e-ci` is the atomized form of `e2e`), `verify-consumer`
  where a project has consumer-facing entry points, `patch-package-exports`
  where it ships non-TS assets, and `compodoc` and `build-storybook` where it
  has a docs site.
- Variables and secrets: `USE_NX_CLOUD` (variable), `NX_CLOUD_AGENTS` (variable,
  optional), `NX_CLOUD_ACCESS_TOKEN` (secret), `SONAR_TOKEN` (secret),
  `RELEASE_APP_CLIENT_ID` (variable) and `RELEASE_APP_PRIVATE_KEY` (secret).

**Where this differs from the planned list.** The list of declarations the
cutover planned and the applied files differ in these ways; the files win.

- `nx.json#release` is more than a bare declaration: `task version` also needs
  `release.version.preVersionCommand` and each project's
  `release.version.manifestRootsToUpdate`.
- The cloud path runs `e2e-ci`, the atomized target; only the local path runs
  `e2e`.
- The workflows also read `.nx/workflows/agents.yaml` (the Node image) and
  `uv.lock` (whether the agents install uv), and `.github/actions/setup` reads
  `.nvmrc` and `packageManager`.
- `task ci:internal-ranges`, run by `validate`, requires members to depend on
  each other by `workspace:^` or `workspace:~`. ngkit's manifests use
  `workspace:^` (`ng-bootstrap` on `ng`, `ng-demo` on both), so this
  declaration is met.
- No workflow calls `task ci:consumer`; ngkit's `verify-consumer` targets run
  `tools/scripts/verify-consumer.mjs`, and `ci:smoke` and `ci:release:verify`
  run those targets.
