# F4.3 — Accept the screen against a real backend

**Status:** in progress · **Owner:** ngkit · **Epic:** [E4](index.md)

**Depends on:** a server library, pinned by version or git ref, that implements every row of the standards table and installs outside its own repository. The pin lives in the fixture's own manifest.

Run `ng-demo`'s e2e suite against a real backend that follows the standards in [Resource screen](../../../architecture/resource-screen.md), in place of the demo's mock `/api`. The backend serves one full resource: list with `orderBy`, get, create, patch with `ETag`, delete, `:batchDelete`, `:import` (with `validateOnly`), `:importTemplate` and export. The fixture is ngkit's own test code, like the consumer fixtures of `ng:verify-consumer`.

## Design

Recorded by S4.3.1 (2026-09-28).

**Stack: Django with Django REST Framework, using `rn-forge-django`.** It is the only server library available for this that has a handler for every operation in the standards table: list with `orderBy`, get, create, `ETag` and `If-Match`, `Idempotency-Key`, `:batchCreate`, `:batchDelete`, `:import` with `validateOnly`, `:importTemplate` with `prefill`, export, and RFC 9457 problem bodies. The FastAPI library has export and import parsing only, so a FastAPI fixture would hand-write `:importTemplate` and the batch routes. That would test the fixture's code, not a library's, and the point of F4.3 is to check the screen against an independent implementation of the standards.

**What the fixture implements itself.** A read of the library's source found two things it does not supply. S4.3.3 confirms them with a request before writing the code:

- **JSON Merge Patch.** The library's JSON parser accepts `application/json` only. `standardDataSource().update` sends `application/merge-patch+json`, which DRF rejects with 415 unless a parser for it is installed. The fixture adds a parser for that media type. It applies RFC 7396 semantics, where a `null` member removes the field, and DRF's partial update does not.
- **`Content-Disposition` in CORS.** The library's exposed-header list omits it, so a cross-origin browser can't read file names. The fixture runs same-origin, so this does not affect it (see Open questions).

**Toolchain.** Python 3.14 or later (the floor `rn-forge-django` 0.4.0 sets) with `uv`, so the e2e job needs both (S4.3.2). The library is pinned in the fixture's own manifest by its release tag, not by a branch. The database is SQLite in a temporary file, recreated for every run.

**Fixture, recorded by S4.3.3 (2026-10-14).** `apps/ng-demo-api/` is a Django project managed by `uv` (`package = false`, Python 3.14, committed `uv.lock`), with `rn-forge-django[drf,transfer]` pinned to its `rn-forge-django-v0.4.0` tag in the fixture's `pyproject.toml`. It serves `products` at `/api/products` on port 8100 with no authentication (so the demo's mock Bearer token is ignored and no CSRF applies), over SQLite in a temporary file that `serve_fixture` deletes, migrates and seeds on every start. The seed is the five products of the demo's mock, ids 1 to 5. How to run it is in the [development guide](../../../guides/development.md#backend-fixture).

The `fixture` build configuration of `ng-demo` replaces `src/environments/environment.ts` with `environment.fixture.ts` (`mockProducts: false`), so the in-browser mock stops answering `/api/products` while `/api/auth/` stays mocked. The `fixture` serve configuration adds `proxy.fixture.json`, which sends `/api` to the fixture, so the browser sees one origin. The default build and serve keep the mock. The dashboard page reads no products, so it is unaffected. `ng-demo-api` has only a `serve` target, so CI's lint, test and build do not need Python.

`POST /api/_test/reset` restores the seed data, the id sequence and the stored idempotency keys; the e2e suite (S4.3.4) calls it before each test.

**What S4.3.3 found.**

- **JSON Merge Patch needs no parser.** The first request, `PATCH` with `application/merge-patch+json` and a matching `If-Match`, answered 200 from the library's own `BaseModelViewSet`, which ships `MergePatchMixin` and a merge-patch parser as of 0.4.0. `application/json` is a 415 with `Accept-Patch`. A `null` member sets a nullable field to null; on a required column the merged document fails validation with 422 at `/category`. The gap in the S4.3.1 reading does not exist, so the fixture adds no parser.
- **`Content-Disposition` in CORS** does not apply: the fixture is same-origin.

**What the fixture hand-writes.** Everything else in the table comes from the library.

- **Filters.** `name` (case-insensitive contains) and `category` (exact) are a 10-line filter backend; the library has no per-field filter helper.
- **`ETag` on create.** The library sets it on get and `PATCH` only, so `create` adds it after the idempotent insert.
- **`:importTemplate` negotiation.** A browser's default `Accept` (`application/json, text/plain, */*`) picks JSON, and the library then sends the CSV as a quoted JSON string. The viewset offers only the tabular renderers for that action.
- **Import number errors.** A non-numeric `price` raised `decimal.InvalidOperation`, which the library reports as a row error (`/rows/1`). A `DecimalWidget` subclass raises `ValueError`, so the error points at `/rows/1/price`.
- **Audit fields on import** (`created_by`, `updated_by`) are set in `before_save_instance`.
- **`price` as a JSON number** (`coerce_to_string=False`) and the `POST /api/_test/reset` view.

**e2e suite, recorded by S4.3.4 (2026-10-14).** `playwright.config.mts` starts the fixture and then `ng-demo:serve:fixture` as two `webServer` entries. The database is shared, so the suite runs serially (`workers: 1`, `fullyParallel: false`). Every products test starts from seed: `beforeEach` posts to `/api/_test/reset` through the demo origin before navigating. That route is the one fixture contract the suite relies on besides the standards, so a second fixture (S4.3.6) must provide it too. In the `fixture` build only, the demo's auth interceptor ignores all of `/api/`: the fixture has no auth, and the demo's anonymous credentials made every unmocked call redirect to login. The default build keeps ignoring only `/api/auth/`. A single-row delete also goes through `:batchDelete`.

**Keep the suite backend-agnostic.** The e2e specs talk to `ng-demo` through the browser only and name no backend. S4.3.6 then repeats them against a FastAPI fixture without changing them.
