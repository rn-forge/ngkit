# S19.8.2 — Exercise Bootstrap as an installed consumer

Brief for
[S19.8.2](../F19.8-boundaries-and-consumers.md#s1982-exercise-bootstrap-as-an-installed-consumer),
at `0e845e7`.

## Goal

`ng-bootstrap` is the only publishable library with no `verify-consumer` target,
so nothing proves its packed tarball installs, compiles and starts outside the
workspace's path aliases. Give it a consumer matrix and a hook that builds a
real Angular application from the packed `ng-bootstrap` and `ng` tarballs, and a
Playwright project that renders that application in a browser.

## Settled

- Acceptance (F19.8, S19.8.2): a temporary standalone application installs
  packed `ng-bootstrap` and `ng` with resolved internal peers, imports the
  published entry points and theme, and builds/renders representative root,
  form and CRUD components. The Angular floor/current cells and the
  zone/zoneless modes are declared explicitly. Browser coverage proves startup
  import ordering and plugin availability; a namespace import alone is not a
  render check. Existing `ng` imports/storage and Tailwind plain/bridge
  builds, CSS cascade and accessibility coverage stay. The change uses F17.5's
  matrix/hook contract and neither restores the deleted
  `tools/scripts/verify-consumer.mjs` nor changes release mode.
- The contract (F17.5,
  `docs/architecture/release-pipeline.md#consumer-verification`,
  `.rn-forge/kiln/standard.md` "For a publishable library's consumer check"):
  a project adds `"verify-consumer": {}` to its `project.json` and declares
  `workspace-ci.consumer` (`dependencies`, `preload`, `cells`, `hook`) in its
  source `package.json`. `task ci:consumer -- <projectRoot>` installs the
  project's own packed tarball into
  `dist/consumer-fixtures/<tarball>/<cell>/`, asserts no `workspace:` range
  was installed, imports every JavaScript entry point under Node (preloads
  first), then runs the hook as a single `.mjs` file copied into the fixture
  and run there with `<fixture-dir> <cell>`. A hook imports no sibling file.
  All of this is kiln's (`kiln-devops consumer`, pinned by `[kiln] ref` in
  `.rn-forge/kiln/config.toml`); this story edits none of it.
- Matrix (decided in this brief; the supported range is ADR-0002's "tested
  matrix: 22.0.6 and 22.1.7, each with zone and zoneless change detection",
  and the peers are `^22.0.6`): four cells named like `ng`'s, `22.0-zone`,
  `22.0-zoneless`, `22.1-zone`, `22.1-zoneless`. 22.0.6 is the floor, 22.1.7
  the current tested cell. No 22.2 cell: the workspace builds with 22.2.x, but
  the declared matrix, and so `ng`'s and `ng-tailwind`'s, stops at 22.1.7.
- Internal peer (decided in this brief, prototyped): `ng-bootstrap`'s tarball
  carries `@rn-forge/ng` as `^0.5.0` (`dist-resolve` rewrites `workspace:^`),
  and `ng` is not on any registry (npm is disabled), so `npm install` of the
  fixture fails unless the cell supplies `ng` itself. Each cell therefore
  lists `"@rn-forge/ng": "file:../../../tarballs/rn-forge-ng-<version>.tgz"`.
  The path is relative to the fixture directory
  `dist/consumer-fixtures/<tarball>/<cell>/`, so it reaches `dist/tarballs/`;
  npm copies the tarball (it does not symlink), and the same path works in
  `verify-release`, where the release tarballs are downloaded to
  `dist/tarballs/`. The `<version>` is the one in `libs/ng/package.json`; a
  version bump must edit the four cell strings (the release runbook gets one
  line saying so). A stale string fails loudly in the pull request's `smoke`
  job (`ENOENT` for the named tarball). Teaching kiln a sibling-tarball
  placeholder would remove the string; that is a kiln request, not this story.
- Node entry-point import (prototyped against the 0.5.0 tarballs): kiln's import
  of every `ng-bootstrap` entry point fails under plain Node with
  `jQuery requires a window with a document`, because the library imports
  `jquery` statically. A `preload` entry runs before the entry points, so the
  cells preload a DOM: `global-jsdom/register`, with `jsdom` and
  `global-jsdom` in the shared cell `dependencies`. With it, all five entry
  points import (`@rn-forge/ng-bootstrap`, `/auth`, `/crud`, `/form`,
  `/shell`). These two packages live only in the throwaway fixtures'
  manifests, not in the repository's `package.json` or lockfile.
- Browser coverage attaches as `ng-tailwind-e2e` does: a `consumer-fixture`
  target on the library runs `task ci:consumer -- <root> --cell <cell>`, and a
  new Playwright project's `webServer` runs that target and serves the
  fixture's `out/browser` with the existing static server
  `apps/ng-tailwind-e2e/serve.mjs` (`ROOT`, `PORT`, `SPA=1`). Two fixtures are
  served, the floor in zone mode (`22.0-zone`) and the current in zoneless
  mode (`22.1-zoneless`), so both extremes are exercised in a browser; the
  four-cell build proves the rest.
- Startup ordering and plugins: `provideRnForgeBootstrapConfig` registers one
  app initializer that sequentially loads the Bootstrap bundle, jQuery as the
  `jQuery`/`$` globals, bootstrap-table and its extensions, then (when
  `table.treegrid`) jquery-treegrid, then `ng-bootstrap-scripts`
  (`libs/ng-bootstrap/src/lib/bootstrap.config.ts:74-91`,
  `src/lib/table/bootstrap-table-loader.ts`,
  `src/lib/table/treegrid-loader.ts`). The theme is
  `@use '@rn-forge/ng-bootstrap/assets/theme';`
  (`libs/ng-bootstrap/assets/README.md`, `apps/ng-demo/src/styles.scss`);
  consuming apps need no `scripts` entry.

## Result
