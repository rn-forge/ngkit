# S19.5.1 — Resolve options through one tested path

Brief for
[S19.5.1](../F19.5-configuration-and-widgets.md#s1951-resolve-options-through-one-tested-path),
at `50f0020`.

## Goal

Pin the observable option-resolution contract of `ConfigurableComponent` and
`ConfigurerService` with tests, then remove the comparisons that run on
references that cannot differ, which the S19.3.2 baseline shows are about half
of every unchanged-content resolution. No observable behaviour changes.

## Settled

- The story's acceptance (F19.5, S19.5.1) and the epic's Scope constraints:
  public imports, subclass hooks and wire formats stay; no dependency; no
  general configuration framework. ADR-0001 (no dependency) and ADR-0002 (the
  presentation library keeps its own resolution; nothing moves to `ng`) hold.
- F19.3 S19.3.1 (closed): a correctness case gets a failing pre-fix regression
  through the public API, then a passing run. This story fixes no correctness
  case, so its characterization tests pass before the change; only the
  operation-count tests in "Tests first" (H) fail before it.
- F19.3 S19.3.2 (closed, harness merged at `b3151a7`): owner criteria, settled
  2026-11-18. After the change, `diff`, `merge`, `componentOptions` and
  `configureOptions` counts per read, change, override and instance are no
  higher than baseline, with `diff` per input change no higher than table
  26/64/212 and form 15/37/127 at S/M/L, and the median time is within +10% at
  M and L for W2, W3 and W4. No improvement percentage is required.
- **Array contract: unchanged (settled).** Resolution is element-wise everywhere
  (lodash `merge`, see Current behaviour); only the accumulation of runtime
  overrides in `mergeOptions` replaces arrays. A shorter or empty array
  therefore never shortens or clears a default, global or input array. This
  brief keeps that behaviour, so no migration guidance is needed. A contract
  that lets a shorter or empty array replace is out of scope (see below).
- **`updateOptions(undefined)` stays a no-op (settled).** The method's doc says
  it clears; the code ignores `undefined`, and `TableComponent.render()`
  (`table/table.component.ts:187-188`) calls
  `this.updateOptions(updatedOptions)` with an optional argument, so a plain
  `render()` relies on the no-op to keep runtime overrides. Making it clear
  would change `render()`. F19.2 owns the docstring fix ("agrees with its
  implementation"); this story does not touch that docstring.
- **Aliasing stays (settled).** Option objects are treated as immutable values:
  a caller that mutates an input or override object in place, without passing
  a new reference, gets no recompute. Cloning on every comparison would raise
  cost above the criteria and is not done.
- **Callback-only changes stay undetected (settled for this story).** The diff
  skips functions, so a changed callback is seen only together with another
  change. Comparing function identity would recompute on every evaluation of
  the harness fixtures and of `CrudManager.deleteModalOptions()` (each builds
  fresh closures per evaluation), raising `merge` and `configureOptions` above
  baseline. Not changed here; see Out of scope.

## Current behaviour

Line numbers are at `50f0020`;
`libs/ng-bootstrap/src/lib/bootstrap.component.ts` is unchanged since `bfd1392`.
Observed with a scratch spec (deleted), a `ConfigurableComponent` subclass with
defaults `{ list: [1,2,3,4], items: [{a:1},{a:2}], n: {x:1,y:2} }` and global
config `{ n: { y: 9 } }`.

- **Service.** `ConfigurerService` (`:62-159`, root singleton) holds
  `defaultsCache` (per `configKey`), `inputsCache`, `overridesCache` and
  `finalOptionsCache` (per `instanceId`) (`:65-68`). `componentDefaults`
  (`:81-104`) merges defaults and global config once per key.
  `componentOptions` (`:106-158`) reads `component.options()`; when the
  instance has a cached input it runs `ObjectUtil.diff(cached, input)`
  (`:113-119`), likewise for `overrides` (`:125-131`), stores a changed object
  by reference (`:121`, `:133`), returns the cached final object when neither
  changed (`:136-138`), else `merge({}, defaults, input)` then
  `merge(merged, overrides)` (`:140-145`), calls
  `component.configureOptions(final)` (`:147`) and stores the result (`:156`).
  `destroyInstance` (`:75-79`) deletes the three per-instance entries.
- **Component.** `ConfigurableComponent` wraps the call in
  `computed(() => componentOptions(this, this._updatedOptions()), { equal: (a, b) => isEmpty(ObjectUtil.diff(a, b)) })`
  (`:206-213`). Angular calls `equal` on every recompute, including when the
  service returned the cached object, so the third diff compares an object
  with itself. `ngOnDestroy` calls `destroyInstance` (`:231-234`).
  `updateOptions` sets the overrides signal and ignores `undefined`
  (`:258-267`); `mergeOptions` uses
  `mergeWith({}, current, updates, arrays replace)` (`:273-284`);
  `clearOverrides` sets `{}` (`:287-291`).
- **`ObjectUtil.diff`** (`libs/ng/core/src/lib/core.utils.ts:173-244`):
  recursive; skips a function in the source (`:215`), treats `null` and
  `undefined` as equal (`:210`), compares dates by time (`:226`). Its only
  production callers are the three sites above.
- **Duplicate work (baseline, S19.3.2).** Three top-level `diff` calls per
  change in W2-same, W3 and W4-fresh (input against cache, overrides against
  cache, the computed's `equal`), and the totals are about twice the input
  walk: table W2-same `3000` top / `26,64,212` total per change at S/M/L, form
  `15,37,127`. In W2-same the input diff is the only one that can differ: the
  override object is the same `{}` reference as the cache, and the `equal`
  compares the cached final object with itself. In W3 the input is the same
  reference on every operation, so the whole input walk (table 12/31/105
  nodes, form 7/18/63) is repeated for nothing. W1 (reads), W4-memoized and W5
  (mount/destroy) already run no diff.
- **Precedence and arrays (observed).** Defaults, then global, then input, then
  override, each merged with lodash `merge`, which merges arrays by index:
    - input `{list:[9,8]}` resolves `[9,8,3,4]`; input `{list:[]}` resolves
      `[1,2,3,4]`; input `{items:[{a:10}]}` resolves `[{a:10},{a:2}]`;
    - `updateOptions({list:[7]})` resolves `[7,2,3,4]`;
    - `mergeOptions({list:[5,6]})` after `updateOptions({list:[7]})` resolves
      `[5,6,3,4]` (the override array was replaced, then merged by index onto
      the defaults); `mergeOptions({list:[]})` then resolves `[1,2,3,4]`;
    - `updateOptions` replaces the whole override set (keys of the previous
      override disappear); `updateOptions(undefined)` leaves it as it was;
      `clearOverrides()` returns to defaults, global and input;
    - the hook ran once per recompute and `c.s ??= 'hooked'` is visible in
      `config`.
- **Other observations.** A callback is copied by reference, never cloned. A
  leaf `undefined` in an input does not override a default. After
  `fixture.destroy()` the three per-instance caches are empty and reading
  `config` does not repopulate them. A callback-only change is not detected
  (input swap `cb1` to `cb2` kept `cb1`; an override `cb1` over an input `cb2`
  kept `cb2`, because both the service diff and the computed's `equal` skip
  functions). An in-place mutation of an input or override object with the
  same reference is not detected. Instances are independent;
  `defaultOptions()` runs once per `configKey` per service.
- **Hook consumers** (`configureOptions` mutates the cached final object): table
  `table/table.component.ts:92-127`, form
  `form/src/lib/form/form.component.ts:113-118` (its constructor effect,
  `:85-107`, rebuilds the group only when the control-key string changes),
  navbar, offcanvas, header, user settings.
- **Tests today.** No spec covers `bootstrap.component.ts` directly. The
  measurement harness lives in `libs/ng-bootstrap/src/lib/measure/` and runs
  only with `NGKIT_MEASURE` set.

## Change

- **Change:** `libs/ng-bootstrap/src/lib/bootstrap.component.ts`, three
  reference short-circuits, no other logic:

    1. `componentOptions`: run the input diff only when the cached input is not
       the same reference as `inputOptions` (same reference means unchanged);
    1. the same for the overrides diff;
    1. the computed's `equal` becomes `a === b || isEmpty(ObjectUtil.diff(a, b))`.

    Keep the call sites in this file and do not change `ObjectUtil.diff`: the
    S19.3.2 harness counts calls to `ObjectUtil.diff`, so a skipped call must be
    a call not made. A same-reference comparison of an object with itself is
    always empty, except for a `NaN` leaf (`NaN !== NaN` makes `diff(a, a)`
    non-empty); with the short-circuit such an object is no longer treated as
    changed on every read, which is the only difference.

- **Change:** edit the `ConfigurerService` class comment (`:47-59`) only, to
  state the contract the tests pin: arrays merge by index at resolution (a
  shorter or empty array does not shorten or clear), option objects are
  treated as immutable values (an in-place mutation is not seen), changes are
  detected by content and ignore functions (a callback is picked up together
  with another change), and results are cached per instance and released on
  destroy. Do not edit the `updateOptions` docstring (F19.2).

- **Change:** new `libs/ng-bootstrap/src/lib/bootstrap.component.spec.ts` (see
  Tests first).

- **Expected count effect** (per operation; the harness figures govern, and
  every figure below is a deterministic count, not a timing claim):

    | Workload | `diff` top-level, before to after | `diff` total, table S/M/L and form S/M/L, after (before) |
    | -- | -- | -- |
    | W2-same, W4-fresh | 3 to 1 | table about 12/31/105 (26/64/212); form about 7/18/63 (15/37/127) |
    | W2-leaf | 3 to 2 | at or below baseline; the override-cache diff is skipped |
    | W3 update/merge, content unchanged | 3 to 1 | about 2 to 5 (27/65/213 table, 16/38/128 form): the override payload only |
    | W3 update/merge, content changed | 3 to 2 | baseline minus the input walk |
    | W1, W4-memoized, W5 | 0 to 0 | unchanged |

    `merge`, `mergeWith`, `componentOptions` and `configureOptions` counts do not
    change in any workload (a skipped diff only ever skipped an "unchanged"
    verdict). The CRUD marked-dirty variant (form with a fresh object per
    template evaluation) is expected to fall from 3000/8000 to about 1000
    top-level calls.

- **Leave alone:**

    - `libs/ng/core/src/lib/core.utils.ts` (`ObjectUtil.diff` and its spec: a
      public, tested utility);
    - the four caches, their per-instance keys, `destroyInstance` and
      `ngOnDestroy`: they already release everything on destroy (see Tests first
      G); restructuring them into signals or into the component is not supported
      by the baseline and is not done;
    - the two `merge` calls in `componentOptions` and the `mergeWith` customizer
      in `mergeOptions`: the harness derives its `merge` count from "two per
      recompute", and folding them would change nothing the baseline asks for;
    - `configureOptions` and `defaultOptions` of every widget, the table and form
      specs, `table.component.ts` `render()`;
    - `libs/ng-bootstrap/src/lib/measure/` (do not edit the harness);
    - any generated file.

## Tests first

All in the new `libs/ng-bootstrap/src/lib/bootstrap.component.spec.ts`
(`describe` blocks as lettered). Write them first and run them against the
unchanged code. Use a standalone probe component `rnf-config-probe` extending
`ConfigurableComponent<ProbeOptions>` (declare `ProbeOptions` as a `type` alias
so it satisfies `ConfigOptions`), `configKey = 'tt'`, defaults
`{ list: [1,2,3,4], items: [{a:1},{a:2}], n: {x:1,y:2} }`, a `configureOptions`
that counts calls and does `c.s ??= 'hooked'`, and the global config
`{ provide: RN_FORGE_BOOTSTRAP_CONFIG_TOKEN, useValue: { tt: { n: { y: 9 } } } }`.
Create it with `TestBed.createComponent`, feed it with
`fixture.componentRef.setInput('options', ...)`, read `component.config`;
`TestBed.resetTestingModule()` in `afterEach`. Keep every expected value below;
if a real run contradicts one, record the observed value in Result and stop (do
not change production code to satisfy a test, except the change above).

Characterization tests (A to G): they pass before and after.

- **A. precedence.** Defaults plus global: `n` is `{x:1,y:9}`, `list`
  `[1,2,3,4]`, `s` `'hooked'`. Input `{n:{y:5}}` gives `{x:1,y:5}`. Input
  `{n:{x:3}}` then `updateOptions({n:{x:5}})` gives `{x:5,y:9}`;
  `clearOverrides()` gives `{x:3,y:9}`. An input leaf `undefined` (fresh
  instance, `{n:{x:undefined}}`) leaves the default `x: 1`.
- **B. arrays (the settled decision).** Input `[9,8]` gives `[9,8,3,4]`; input
  `[]` gives `[1,2,3,4]`; longer input `[1,2,3,4,5]` gives five elements;
  input `items:[{a:10}]` gives `[{a:10},{a:2}]`. `updateOptions({list:[7]})`
  gives `[7,2,3,4]`; `updateOptions({list:[]})` gives `[1,2,3,4]`.
  `updateOptions({list:[7,7,7]})` then `mergeOptions({list:[5,6]})` gives
  `[5,6,3,4]` (replacement inside the overrides, not `[5,6,7,4]`), then
  `mergeOptions({list:[]})` gives `[1,2,3,4]`.
- **C. override semantics.** `updateOptions({list:[7]})` then
  `updateOptions({n:{x:5}})` drops the `list` override (back to `[1,2,3,4]`).
  `mergeOptions({n:{x:5}})` then `mergeOptions({n:{y:6}})` keeps both
  (`{x:5,y:6}`). `updateOptions(undefined)` after `updateOptions({n:{x:5}})`
  leaves `x: 5`. `clearOverrides()` removes every override.
- **D. callbacks.** `config.cb === cb` for an input callback and for one passed
  to `mergeOptions` (identity, not a copy); `config.items[0].fn === fn` for a
  callback inside an array element (the element is cloned, the function is
  not). A callback replaced in the same input object change as another leaf
  (`{cb: cb2, s: 'x'}` after `{cb: cb1}`) resolves `cb2`. Do not pin the
  callback-only swap (a known limitation, see Out of scope).
- **E. hook.** `configureOptions` runs once for the first read; not again for a
  second read, nor for a new input object with equal content; once more after
  a leaf change and after an override change; it receives the merged object
  (defaults, global, input and override applied), and what it adds (`s`) is in
  `config` and in neither the input nor the override object.
- **F. immutability and aliasing.** After resolving with a hook that mutates
  nested array elements (`c.items?.forEach(i => (i.a = 99))`), the input
  object, the override object and the global config deep-equal their
  pre-resolution snapshots, and a second instance (fresh input) still sees
  `items` `[{a:1},{a:2}]` (defaults not mutated). Replacing an input by a new
  object with a changed leaf is detected; mutating the same input object in
  place and setting it again is not (the settled aliasing contract, named in
  the test as a documented limitation).
- **G. instances and destroy.** Two instances with different input and override
  resolve independently, and `defaultOptions()` runs once per service for the
  key (spy). After `fixture.destroy()` the service's `inputsCache`,
  `overridesCache` and `finalOptionsCache` hold no entry for that `instanceId`
  (read through a cast to
  `{ inputsCache; overridesCache; finalOptionsCache }`, as the harness's
  `cacheSizes` does), the other instance's entries and `config` are untouched,
  and the other instance still updates after the first is destroyed.

Operation-count tests (H): spy on `ObjectUtil.diff`
(`vi.spyOn(ObjectUtil, 'diff')` calling through; count top-level calls with a
depth counter, as `option-resolution.count.measure.spec.ts` does). Resolve once

- **H1. unchanged read** (`config` read twice): 0 calls. Passes before.
- **H2. new object, equal content, as input**: exactly 1 top-level call. **Fails

## Out of scope

- A general configuration framework, a signal-owned replacement of the caches,
  moving per-instance state into the component, or a different cache key.
- Changing the array contract (shorter or empty arrays replacing), changing
  `mergeOptions` or `updateOptions` semantics, making
  `updateOptions(undefined)` clear, or editing its docstring.
- Making callback-only changes detectable (compare function identity). It is a
  known limitation: input `cb1` swapped to `cb2` alone keeps `cb1`; an
  override `cb1` over an input `cb2` alone keeps `cb2`. Record it in Result
  under "Deviations or findings"; do not fix it here.
- Cloning input or override objects to detect in-place mutation.
- Editing `ObjectUtil.diff`, the harness, any widget's `configureOptions`, the
  CRUD manager's option builders, or the F19.2 docstrings.
- Performance claims beyond the harness figures compared against the criteria.
