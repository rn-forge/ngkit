# S19.7.2 — Reset from fresh defaults and notify consumers

Brief for
[S19.7.2](../F19.7-settings-lifetimes.md#s1972-reset-from-fresh-defaults-and-notify-consumers),
at `e547f79`.

## Goal

Make `UserSettingsService.clearStoredSettings` rebuild the effective settings
from a fresh copy of the declared defaults, so exported defaults and other
service instances are never mutated, and notify live listeners of their reset
values, so rendered widgets agree with the emptied storage.

## Settled

- The story's acceptance (F19.7, S19.7.2) and the epic's Scope constraints: keep
  public imports and wire formats; no dependency; E7's deferred theme
  controller is not introduced. No new state-management framework (F19.7,
  S19.7.1 acceptance).
- F19.3 S19.3.1 (closed): each correctness case gets a failing pre-fix
  regression through the public API or the rendered host, then a passing
  post-fix run.
- F19.7 S19.7.1 (closed): `registerChangeListener` returns a disposer and
  `rnf-color-mode` and `rnf-header` release it on destroy. That API stays as
  it is.
- Decided here (owner-scheduled scope, reviewer ruling 2026-11-18): the
  effective value after a clear is `DEFAULT_USER_SETTINGS[key]` for the three
  standard keys and `undefined` for any other key. A live listener of a custom
  key therefore receives `undefined` on clear, the same value a listener
  registered on a missing key already receives at registration (the existing
  comment "could be undefined" in `registerChangeListener`). No consumer in
  the repository registers a custom key.
- Not decided here and not touched: whether `rnf-header` should show the stored
  `navbarColor` on mount, which would change precedence between the header
  config `navbarColor` and the stored user setting. See Out of scope.

## Current behaviour

Line numbers are at `e547f79`, in
`libs/ng-bootstrap/auth/src/lib/user/settings/settings.service.ts` unless noted.
Observed with a scratch spec (deleted) through the public service API.

- **Defaults object is shared after a clear.** `clearStoredSettings`
  (`:100-108`) assigns `this._currentUserSettings = DEFAULT_USER_SETTINGS`
  (`:104`), the exported constant (`settings.types.ts:71`), not a copy. The
  constructor path (`buildCurrentUserSettings`, `:133-137`) does copy, with
  `merge({}, DEFAULT_USER_SETTINGS, stored)`. After a clear, `updateSetting`
  (`:78-79`, `this.currentUserSettings[key] = value`) writes into the exported
  constant. Observed: update `colorMode` to `dark`, clear, update to `light`:
  `DEFAULT_USER_SETTINGS` reads `{"theme":"default","colorMode":"light",...}`;
  a second clear then leaves `currentUserSettings.colorMode === 'light'`, not
  the declared `'auto'`. Clear, update, clear does not restore the defaults.
- **Other instances see the mutation.** A service built afterwards (a new
  `TestBed` injector, or any later `new` of the root service) merges the
  mutated constant: after instance A does clear then
  `updateSetting('navbarColor', 'danger')`, instance B's
  `currentUserSettings.navbarColor` is `'danger'` instead of `'default'`. The
  mutation also leaks across tests in one spec file, so a test must compare
  against a literal, not against the exported constant.
- **Clear does not notify.** `clearStoredSettings` never touches
  `_changeListeners`. A listener registered on `colorMode` after an update to
  `dark` is called with nothing on clear (observed: zero calls), so a live
  `rnf-color-mode` and `rnf-header` keep the old value while storage and
  `currentUserSettings` hold the default.
- **Late registration gets a stale value.** `registerChangeListener` (`:56-67`)
  reuses the existing `BehaviorSubject` for the key (`ObjectUtil.setDefault`,
  `libs/ng/core/src/lib/core.utils.ts:153-163`, only creates one when absent),
  so its last emitted value wins over `currentUserSettings`. Observed:
  register, update to `dark`, clear, register a second listener: it is called
  with `'dark'`, not `'auto'`. This disappears once clear notifies the
  subjects.
- **Custom keys.** After clear a custom key set earlier (`x`) is gone from
  `currentUserSettings` (`undefined`) but its listener is not told.
- **Already correct (keep).** Clear persists `{}` through
  `localStorageService.setJSON(USER_SETTINGS_STORAGE_KEY, ...)` (`:106-109`);
  observed `{}` in storage after a clear. `updateSetting` persists and
  notifies its own key only (`:73-92`). Missing stored values deliver the
  default at construction (merge) and `undefined` for an unknown key.
- **Consumers.** `rnf-color-mode`
  (`libs/ng-bootstrap/shell/src/lib/color-mode/color-mode.ts:56-70`) applies
  the stored mode once on init and then through the listener, which ignores an
  empty value (`:65`). `rnf-header`
  (`libs/ng-bootstrap/shell/src/lib/header/header.component.ts:94-100`) sets
  `navbarColor` from the listener. Both therefore follow a clear as soon as
  the service notifies; no consumer change is needed. `UserSettingsComponent`
  (`libs/ng-bootstrap/auth/src/lib/user/settings/settings.component.ts:188-192`)
  calls `clearStoredSettings` and rebuilds its form options from
  `storedUserSettings`, which is already `{}`.

## Change

- **Change:**
  `libs/ng-bootstrap/auth/src/lib/user/settings/settings.service.ts`,
  `clearStoredSettings` only:
    1. set `_storedUserSettings = {}` (as now);
    1. rebuild the effective settings with `this.buildCurrentUserSettings()`
       instead of assigning `DEFAULT_USER_SETTINGS`, so the result is a fresh
       copy;
    1. persist `{}` (as now), before notifying;
    1. for every key in `_changeListeners`, call
       `.next(this._currentUserSettings[key])`. Update the method's doc comment
       to say it resets to the declared defaults and notifies live listeners. No
       new method, field or dependency.
- **Change:**
  `libs/ng-bootstrap/auth/src/lib/user/settings/settings.service.spec.ts` and
  the two shell specs named under Tests first.
- **Leave alone:** the disposer API of `registerChangeListener` (S19.7.1);
  `updateSetting`'s behaviour; `settings.types.ts` (do not freeze or clone the
  exported defaults, they are public); `color-mode.ts`, `header.component.ts`
  and the header's constructor `effect`; `settings.component.ts` and its
  "Current Settings" table; E7's deferred theme controller; behaviour for
  unrelated custom keys and missing values other than the `undefined` delivery
  on clear settled above.

## Tests first

Write these first and run them against the unchanged service; each must fail for
the reason given, then pass after the change. Compare against the literal
`{ theme: 'default', colorMode: 'auto', navbarColor: 'default' }`, never against
`DEFAULT_USER_SETTINGS`, because the unfixed service mutates it and leaks into
later tests; run each failing case alone (`-t '<name>'`) to confirm it fails by
itself.

In `settings.service.spec.ts`, a new `describe('UserSettingsService reset')`,
using the existing `TestBed` setup:

- **`restores the declared defaults on every clear`**: update `colorMode` to
  `dark`, clear, update to `light`, clear; assert `currentUserSettings` equals
  the literal and `DEFAULT_USER_SETTINGS` equals the literal. Fails before:
  `colorMode` is `'light'`.
- **`does not change another service instance`**: with instance A, clear then
  update `navbarColor` to `danger`; build instance B in a fresh `TestBed`;
  assert B's `currentUserSettings.navbarColor` is `'default'`. Fails before:
  `'danger'`.
- **`clear persists the empty override set`**: update, clear; assert
  `localStorageService.getJSON(USER_SETTINGS_STORAGE_KEY, ...)` is `{}` and
  `storedUserSettings` is `{}`. Passes before (pins the kept behaviour).
- **`clear notifies live listeners with the reset value`**: register on
  `colorMode` and `navbarColor`, update both, clear; assert each listener's
  last call is `'auto'` and `'default'`, once per key for the clear. Fails
  before: no call.
- **`does not notify a disposed listener on clear`**: register, dispose, update,
  clear; assert the disposed callback saw nothing after dispose. Passes
  before; pins the S19.7.1 contract against the new notification loop.
- **`a listener registered after a clear gets the reset value`**: register,
  update to `dark`, clear, register a second listener; assert it receives

- **`a custom key is notified undefined on clear and other keys are untouched`**:
  register on `x` and update it, clear; assert `x`'s last call is `undefined`,

  updated still holds its default. Fails before: no call on `x`.
- **`ordinary updates keep working after a clear`**: clear, update `colorMode`;
  assert stored, current and the listener hold the new value and the defaults

## Out of scope

- **Header precedence (open decision, not for the implementer).** On mount,
  `rnf-header` shows `config.navbarColor` and not the stored value: the
  constructor `effect` (`header.component.ts:87-89`) runs after `ngOnInit`
  (`:92-101`) has delivered the current value and overwrites it. Showing the
  stored value on mount would make a never-chosen default (`'default'`) beat a
  configured `navbarColor` (for example `'primary'`, the example in
  `libs/ng-bootstrap/src/lib/bootstrap.config.ts:71`), changing the precedence
  between configuration and the stored user setting. Do not touch the
  `effect`, the listener or the config handling. The tests above do not depend
  on it: they mount with no configured `navbarColor`, so config and default
  coincide.
- The settings screen's "Current Settings" table
  (`settings.component.ts:122-148`) is built once from `currentUserSettings`
  at construction and is not rebuilt after a save or a clear. That is separate
  from this story and from the reset contract; leave it.
- Cloning or freezing `DEFAULT_USER_SETTINGS`, changing `storedUserSettings` /
  `currentUserSettings` getters to return copies, or any other API change.
- A theme controller, a signal-based store or any E7 work; the docs corrections
  F19.2 owns (the `updateSettings` docstring); E5's auth-UI replacement.
