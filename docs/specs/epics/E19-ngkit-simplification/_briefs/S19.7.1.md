# S19.7.1 — Release settings observers with their views

Brief for
[S19.7.1](../F19.7-settings-lifetimes.md#s1971-release-settings-observers-with-their-views),
at `91d9713`.

## Goal

`UserSettingsService.registerChangeListener` subscribes every caller for the
life of the service and gives them no way to leave, so each mounted
`rnf-color-mode` and `rnf-header` leaves a live observer behind when it is
destroyed. Make the registration return a disposer and have both consumers
release it when their view is destroyed.

## Settled

- The story's acceptance (F19.7, S19.7.1) and the feature's note to coordinate
  with E5: E5 is closed (v0.5.0, 2026-11-18). The settings owner that survives
  is `UserSettingsService` in `@rn-forge/ng-bootstrap/auth`
  (`libs/ng-bootstrap/auth/src/lib/user/settings/settings.service.ts`); E5 did
  not replace it. Apply the contract there. Do not add a second settings
  service.
- Epic Scope constraints ([E19](../index.md#scope-constraints)): preserve public
  imports; an intentional contract change gets explicit acceptance, a
  changelog entry and a versioning assessment. Avoid replacing the small
  service with a state-management framework (story acceptance): no
  signals-store, no new subject type, no new dependency.
- S19.3.1 (closed): each correctness case's regression is written by the story
  that fixes it, through the public API or a rendered host, and must fail
  before the fix and pass after.
- Shape (decided in this brief, from the code's own patterns): the method keeps
  its name and arguments and returns a disposer, `() => void`. The repository
  already ties teardown to Angular lifetimes with `inject(DestroyRef)` and
  `onDestroy` (`libs/ng/core/src/lib/core.eventstream.ts:126`,
  `libs/ng/core/src/lib/core.loading.ts:140`); consumers call
  `this.destroyRef.onDestroy(dispose)` with it. The service stays free of an
  Angular lifetime parameter, so non-component callers (the demo app, tests)
  can also dispose. Changing the return type from `void` to `() => void` is
  additive: existing callers that ignore the result compile and behave as
  before (apart from the fix, they still never release unless they call it).
- E7's deferred theme controller (decoupling `rnf-color-mode` from
  `UserSettingsService`, `docs/specs/epics/E7-theme-controller/index.md:85`)
  is not introduced and not started by this story.

## Current behaviour

All line numbers are at `91d9713`. `libs/ng-bootstrap/auth` has the service;
`libs/ng` and `libs/ng-tailwind` do not use it (no `registerChangeListener`,
`UserSettingsService` or `updateSetting` reference outside `libs/ng-bootstrap`
and the demo app).

- `libs/ng-bootstrap/auth/src/lib/user/settings/settings.service.ts`:
    - `:40` `_changeListeners`: one `BehaviorSubject<string>` per setting key.
    - `:58-67` `registerChangeListener(key, callback): void`:
      `ObjectUtil.setDefault` creates the key's subject on first use (seeded
      with `currentUserSettings[key]`; later registrations reuse the existing
      subject) and calls `.subscribe(callback)`. The `Subscription` is
      discarded, so there is no disposal. `BehaviorSubject` delivers its latest
      value synchronously on subscribe, which is the current-value delivery the
      tests below must keep.
    - `:72-88` `updateSetting` updates storage and calls
      `_changeListeners[key]?.next(value)`; every subscribed callback runs.
    - `:93-101` `clearStoredSettings` replaces the stored and current objects and
      does not notify. That is S19.7.2; leave it.
- Registered consumers (the only two production callers):
    - `libs/ng-bootstrap/shell/src/lib/color-mode/color-mode.ts:51-67`
      `ColorMode.delayedAfterViewInit` (run from `afterNextRender` in
      `libs/ng/core/src/lib/core.components.ts:43-45`) registers `colorMode`;
      the callback ignores empty values and calls `setColorMode`, which writes
      `data-bs-theme` on the document through `StyleHelper.setColorMode`.
    - `libs/ng-bootstrap/shell/src/lib/header/header.component.ts:90-98`
      `HeaderComponent.ngOnInit` registers `navbarColor`; the callback sets the
      `navbarColor` signal.
- `libs/ng-bootstrap/auth/src/lib/user/settings/settings.component.ts:190,237`
  and `color-mode.ts:90` call `clearStoredSettings` and `updateSetting`. They
  register no listener and need no change.
- `apps/ng-demo/src/app/app.ts:42` injects the service and registers nothing.

### Observed failure

Reproduced at `91d9713` with a scratch spec (since deleted) in the `shell`
secondary entry: create five `ColorMode` fixtures, `detectChanges` and
`whenStable` each (so `delayedAfterViewInit` runs), destroy all five, then
`updateSetting('colorMode', 'dark')`. `matchMedia` must be stubbed first
(`window.matchMedia = () => ({ matches: false, addEventListener() {} })`)
because jsdom has none, and `StyleHelper.setColorMode` throws without it.

- Spying on `StyleHelper.setColorMode`: **5 calls after all five fixtures were
  destroyed**, one per destroyed component. Each component also still writes
  its destroyed signals.
- `_changeListeners['colorMode'].observers.length` was 5 after destroying 5
  fixtures; for `HeaderComponent` created and destroyed 5 times,
  `_changeListeners['navbarColor'].observers.length` was 5.
- So callbacks grow linearly with repeated mount/destroy (a route that
  re-renders the header or colour toggle adds one per visit) and run against
  destroyed views.

## Change

- **Change:**
    - `libs/ng-bootstrap/auth/src/lib/user/settings/settings.service.ts`:
      `registerChangeListener` returns `() => void`. Keep the `BehaviorSubject`
      per key, the `setDefault` creation and the synchronous current-value
      delivery. Capture the `Subscription` and return
      `() => subscription.unsubscribe()`. Disposing twice must be harmless
      (`unsubscribe` already is). Update the doc comment (`@returns` the
      disposer; say the caller must call it when its owner goes away). Do not
      touch `updateSetting`, `clearStoredSettings`, storage, or the
      `storedUserSettings` / `currentUserSettings` getters.
    - `libs/ng-bootstrap/shell/src/lib/color-mode/color-mode.ts`:
      `inject(DestroyRef)` and pass the disposer from `registerChangeListener`
      to `destroyRef.onDestroy(...)` in `delayedAfterViewInit`. Guard against a
      view destroyed before the hook runs: `afterNextRender` is not run for a
      destroyed view, so no extra guard is needed; do not add one unless a test
      shows it is.
    - `libs/ng-bootstrap/shell/src/lib/header/header.component.ts`: the same in
      `ngOnInit`.
    - Add a short changelog/versioning note as described in Rules.
- **Leave alone:** `clearStoredSettings`, defaults handling and reset
  notification (S19.7.2 owns them; its tests will rely on the current
  `registerChangeListener` contract plus the disposer); `updateSetting`
  semantics; `UserSettingsComponent`; `StyleHelper`; the E7 theme-controller
  design; `libs/ng` and `libs/ng-tailwind`; `CHANGELOG.md` (generated at
  release, see Rules).

## Tests first

Write these first and run them against the unchanged code. The service tests
that need a disposer do not compile or run before the change; make them fail by
calling `registerChangeListener` and using the result, or note in the Result
that they fail on the missing disposer. The host tests fail at runtime as
described and are the pre-fix regressions S19.3.1 requires.

1. New `libs/ng-bootstrap/auth/src/lib/user/settings/settings.service.spec.ts`
   (`TestBed.inject(UserSettingsService)` with `localStorage.clear()` in
   `beforeEach`):
    - "delivers the current value immediately": registering returns the stored
      value (e.g. after `updateSetting('colorMode','dark')`, a new listener is
      called once with `'dark'`; with nothing stored, with the default).
    - "delivers later updates to live listeners": two listeners on one key both
      receive the next `updateSetting`; a listener on another key does not.
    - "does not deliver after dispose": dispose one of two listeners, update;
      only the other is called; disposing again does not throw.
    - "repeated register/dispose does not multiply callbacks": register and
      dispose 5 times, register once more; one `updateSetting` calls the live
      listener once and the disposed ones not at all (assert on call counts,
      not on `observers`). Before the fix the disposer is `undefined`, so the
      dispose cases fail.
1. In `libs/ng-bootstrap/shell/src/lib/color-mode/color-mode.spec.ts`: "does not
   apply colour mode after destroy, and repeated mount/destroy does not
   multiply": stub `matchMedia` (as above), spy on `StyleHelper.setColorMode`,
   create and fully render (`detectChanges`, `whenStable`) and destroy several
   fixtures, clear the spy, create one live fixture,
   `updateSetting('colorMode','dark')` and assert exactly one call and
   `data-bs-theme="dark"`. Fails before (5 stale calls plus the live one in
   the observed run). Also: a live fixture shows the current stored value on
   mount.
1. In `libs/ng-bootstrap/shell/src/lib/header/header.component.spec.ts`:
   "ignores navbarColor updates after destroy": a destroyed header's
   `navbarColor` signal is not written after
   `updateSetting('navbarColor','dark')` (read the component's signal through
   a typed test subclass or the rendered navbar class rather than string-keyed
   internals), and a live header picks up the update and the current value on
   mount. Fails before (callback still runs on the destroyed instance).
