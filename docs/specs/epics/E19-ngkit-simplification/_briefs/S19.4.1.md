# S19.4.1 — Permission rebinding renders one view

Brief for
[S19.4.1](../F19.4-core-and-permissions.md#s1941-permission-rebinding-renders-one-view),
at `91d9713`.

## Goal

Make `rnfHasPermission` and `rnfHasAnyPermission` render at most one embedded
view however their input changes, so an allowed-to-allowed rebinding no longer
appends duplicate content. Replace nothing public: the fix is inside the two
directives, and the tests move to a rendered host.

## Settled

- The story's acceptance (F19.4, S19.4.1): both directives render exactly one
  embedded view across repeated allowed inputs, allowed-to-allowed changes and
  deny/allow transitions; a rendered host verifies content and destruction
  instead of asserting private container calls; existing `RNF_PERMISSION`
  vocabulary survives E5.
- F19.3 S19.3.1 (closed 2026-11-18): each F19.4 correctness case gets a failing
  pre-fix regression through its public API or rendered host, then a passing
  post-fix run; this story writes S19.4.1's regressions.
- Epic Scope constraints: preserve public imports and wire formats; no
  dependency; E5 owns the session-auth replacement. E5 explicitly retains the
  permission directives and the `RNF_PERMISSION` vocabulary
  (`docs/specs/epics/E5-session-client-auth/index.md`: "The authorization
  vocabulary already matches the contract"), so they are fixed here, not in
  E5.
- This is a bug fix with no contract change: the public selectors, inputs and
  `Permission` interface stay as they are, so no changelog or versioning
  assessment is needed (the repository has no changelog file).
- Zero or one view is the contract: the template has no context, so an
  allowed-to-allowed change keeps the existing view rather than re-creating it
  (decided here; it is the minimal fix and observably identical).

## Current behaviour

At `91d9713`, `libs/ng/auth/src/lib/auth.directives.ts`:

- `HasPermissionDirective` (`:17-35`): the `rnfHasPermission` input setter
  (`:26-33`) calls `viewContainer.createEmbeddedView(templateRef)` whenever
  the key is allowed (`:27-29`) and `clear()` otherwise (`:32`). It never
  checks for a view it already created.
- `HasAnyPermissionDirective` (`:40-57`): the same shape, setter at `:48-55`
  (`createEmbeddedView` at `:49-51`).

An input setter runs on every change of the bound value, so every change to
another allowed value appends a view. Reproduced with a scratch rendered host
(deleted) holding both directives, using a policy where `a`, `b`, `c`, `d` are
allowed, driving the host through signals and `fixture.detectChanges()`; the
counts are `.querySelectorAll` matches of the guarded content:

| Step | `rnfHasPermission` | `rnfHasAnyPermission` |
| -- | -- | -- |
| first allowed input (`a`) | 1 | 1 |
| allowed to allowed (`a` to `b`) | 2 | 2 |
| allowed to allowed (`b` to `a`) | 3 | 3 |
| denied | 0 | 0 |
| denied to allowed | 1 | 1 |
| allowed to denied | 0 | 0 |

So the observed failure is "2 copies after the second allowed input, 3 after the
third"; `deny -> allow -> deny` already behaves, because `clear()` runs on deny.
Re-binding the same string does not call the setter, so it is not a failing
case; a new array with the same content for `rnfHasAnyPermission` does.

Note for the tests: the library's test environment checks host components as
OnPush-like, so changing a plain host property and calling `detectChanges()` a
second time does not re-run the bindings (the scratch host rendered `1` after
every step until its inputs were signals). The existing spec mutates plain
properties only before the first `detectChanges()`. The new host must hold its
inputs in signals.

Existing spec: `libs/ng/auth/src/lib/auth.directives.spec.ts`. It renders hosts
(`PermHostComponent`, `AnyPermHostComponent`) and asserts content presence and
absence and that the injected policy is called with the bound key(s)
(`calls hasPermission with the bound permission string`,
`spreads the permissions array into hasAnyPermission`). It asserts no
`ViewContainerRef` calls, so nothing there needs replacing for that reason; it
has no rebinding, transition or destruction case. Vocabulary: `RNF_PERMISSION`
is defined at `libs/ng/auth/src/lib/auth.config.ts:71` (default
`AllowAnyPermission`) and survives E5; the directives, `auth.guards.ts`,
`auth.mixins.ts`, `provideRnForgeAuth` and the crud manager all use it.

## Change

- **Change:** `libs/ng/auth/src/lib/auth.directives.ts`. In each setter, create
  the embedded view only when the container is empty, and clear it when
  denied:

    ```ts
    if (allowed) {
      if (this.viewContainer.length === 0) {
        this.viewContainer.createEmbeddedView(this.templateRef);
      }
      return;
    }
    this.viewContainer.clear();
    ```

    Keep the setters, selectors, injected members and public `host` field as they
    are. Keep the file's `/** ... */` doc-comment style; update a directive's
    comment only if it should now say it renders at most one view.

- **Change:** `libs/ng/auth/src/lib/auth.directives.spec.ts`. Add the rendered
  host tests below; keep the existing tests unless a new one supersedes it.

- **Leave alone:** `auth.config.ts`, `auth.types.ts`, `auth.guards.ts`,
  `auth.mixins.ts`, `auth.providers.ts`, `libs/ng/auth/testing`,
  `libs/ng-bootstrap/**`, `libs/ng/auth/src/index.ts`, every `project.json`,
  `tsconfig*.json` and kiln-generated file, and `docs/`.

## Tests first

All in `libs/ng/auth/src/lib/auth.directives.spec.ts`. Use rendered hosts that
hold the bound key or keys in signals, a policy whose answer is a mutable set
(not a fixed mock return), `fixture.detectChanges()` after each change, and
`fixture.nativeElement.querySelectorAll('.guarded').length` as the node count.
No test reads or spies on `ViewContainerRef`. Write these before the fix and run
them; each of the first two per directive must fail as stated.

For `HasPermissionDirective` (describe `HasPermissionDirective`):

1. `renders one view across allowed-to-allowed changes`: start allowed (`a`),
   set `b`, then `a` (all allowed); assert 1 node after each step. Fails
   before the fix with 2 after the second step and 3 after the third.
1. `renders one view across deny and allow transitions`: allowed, denied,
   allowed, denied; assert 1, 0, 1, 0. Passes before the fix (the `clear()`
   path already works); it guards the transition against the fix.
1. `removes the content when the host is destroyed`: render allowed, rebind to
   another allowed key, then `fixture.destroy()`; assert the host element
   holds no `.guarded` node and no error is thrown. Passes before the fix; it
   covers the story's destruction check.

For `HasAnyPermissionDirective` (describe `HasAnyPermissionDirective`), the same
three, with the array input: for the first, rebind to a new array with the same
content (`['a']` then a new `['a']`) as well as to a different allowed array;
the different-array step fails before the fix with 2 nodes and the next with 3,
and the same-content new array fails with an extra copy as well.

Keep the existing eight-line presence/absence tests. The two
`toHaveBeenCalledWith` tests stay: they assert the call to the injected
`RNF_PERMISSION` policy, the public token boundary, not private container state.

Record in `## Result` the observed pre-fix failure of tests 1 (both directives)
and that tests 2 and 3 pass before and after.
