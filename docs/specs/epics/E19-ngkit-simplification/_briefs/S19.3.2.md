# S19.3.2 — Measure before removing machinery

Brief for
[S19.3.2](../F19.3-behavioral-baselines.md#s1932-measure-before-removing-machinery),
at `48e181a`.

## Goal

Record, with a measurement harness that stays out of the default gate, what the
option-resolution machinery (`ConfigurerService` and the `ObjectUtil.diff` calls
around it) costs at representative table and form option sizes, and write the
responsibility and coupling analysis of the CRUD manager. This is a decision
story: you reproduce and compare; the owner decides which simplifications
proceed. No production code changes.

## Settled

- The story's acceptance (F19.3, S19.3.2), F19.5 S19.5.1 (depends on this story)
  and F19.6 S19.6.1 (extracts manager responsibilities "only if S19.3.2
  establishes a useful boundary"), and the epic's
  [Completion](../index.md#completion) rule: a measurement names its workload,
  environment, time, memory and operation counts; fewer lines alone establish
  no performance improvement; no speedup claim comes from static inspection.
- `design.md` ("Remove overlapping ownership only where it helps", "Tests and
  measurements"): operation counts are deterministic and could later become
  tests; noisy time and memory comparisons belong in the brief's `## Result`;
  do not split the 703-line manager merely to lower a metric; name the
  independent responsibility and the crossing state first.
- The owner, not the implementer, chooses the no-regression or improvement
  criteria and whether a simplification proceeds. You propose criteria as
  options (see "Tests first", item 6).
- No dependency is added (epic Scope constraints; ADR-0001). The harness uses
  only `vitest` 4.1.12 (already installed), `@angular/core/testing`, `jsdom`
  (the existing test environment), `lodash-es` and `@rn-forge/ng/core`.
- `vitest bench` is not usable: the project's test target is
  `@nx/angular:unit-test` (`libs/ng-bootstrap/project.json:45`), which has no
  bench option and compiles specs through the Angular builder. The harness is
  therefore a plain spec file gated by an environment variable (decided here,
  verified by prototype at `48e181a`).

## Current behaviour

### Option resolution (what F19.5 targets)

`libs/ng-bootstrap/src/lib/bootstrap.component.ts`:

- `:62-68` `ConfigurerService` (root singleton) keeps four plain-object caches:
  `defaultsCache` (by `configKey`), `inputsCache`, `overridesCache`,
  `finalOptionsCache` (all by `instanceId`).
- `:81-104` `componentDefaults`: one `merge({}, defaultOptions(), global)` per
  `configKey`, cached by key behind a truthiness check on the entry;
  `resetDefaults()` (`:70`) is the only invalidation.
- `:106-158` `componentOptions(component, overrides)`:
    - `:110-122` reads `component.options()`; if the instance has a cached input,
      runs `ObjectUtil.diff(cachedInput, inputOptions)` and tests `isEmpty`;
      stores the new input by reference when changed.
    - `:124-134` the same for `overrides` against `overridesCache`.
    - `:136-138` if neither changed, returns the cached final object.
    - `:140-145` otherwise two `merge` calls (`merge({}, defaults, input)`, then
      `merge(merged, overrides)`), then
      `component.configureOptions(finalOptions)` (`:147`, a hook that subclasses
      use to mutate the resolved object), then stores and returns it.
- `:206-213` `ConfigurableComponent` wraps the call in a `computed` whose
  `equal` is `isEmpty(ObjectUtil.diff(a, b))`: a third diff, run on every
  recompute that yields a new object.
- `:231-234` `ngOnDestroy` calls `destroyInstance` (`:75-79`), which deletes the
  three per-instance cache entries.
- `:258-267` `updateOptions` replaces the overrides signal (`undefined` is a
  no-op although the `Configurable` doc says it clears; observe, do not fix);
  `:273-284` `mergeOptions` uses `mergeWith` with arrays replaced (the only
  array-replacing path); `:287-291` `clearOverrides` sets `{}`.
- `libs/ng/core/src/lib/core.utils.ts:173-193` `ObjectUtil.diff`: recursive walk
  of both objects, building a
  `{missing_in_source, missing_in_target, conflicts}` result; `:196-244`
  `_diffTargetKey` recurses through `ObjectUtil.diff` (`:234`), skips
  functions (`:215`), compares dates by time (`:226`). Its only production
  caller is `bootstrap.component.ts` (`:114`, `:126`, `:212`).
- Consumers of `configureOptions`, which mutate the resolved (cached) object:
  table `libs/ng-bootstrap/src/lib/table/table.component.ts:92-127` (sets
  `uniqueId`, `toolbar`, replaces `disabled` on each linked button, wraps
  `onPostBody`; defaults at `:129-160` include a 4-entry `pageList` and an
  empty `columns`/`toolbarButtons`); form
  `libs/ng-bootstrap/form/src/lib/form/form.component.ts:113-118` (sets
  `classes`; defaults `:120-129`; the constructor effect `:85-107` reads
  `this.config.controls`, rebuilds the group only when the sorted control-key
  string changes). Others: navbar, header, offcanvas, user settings.

How option objects reach it:

- Table: `<rnf-table [options]=...>` input, or `render(updatedOptions)`
  (`table.component.ts:187-196`) calling `updateOptions`, then
  `bootstrapTable(this.config)`.
- CRUD: `crud.component.html:46` binds `manager().tableOptions()`, which
  memoizes its object (`crud.manager.ts:323-370`, `_tableOptions`), so the
  input identity is stable. `crud.component.html:97` binds
  `manager().addUpdateFormOptions()` (`crud.manager.ts:378-383`) and `:109`
  binds `manager().deleteModalOptions()` (`:549-568`); both return a fresh
  `merge(...)` object, with a fresh callback closure for the delete button, on
  every template evaluation. Whether and how often that re-enters
  `componentOptions` is part of what you measure (workload W4).
- Aliasing to observe, not fix: the service stores the caller's input and
  override objects by reference (`:121`, `:133`), so an in-place caller
  mutation is compared against itself and reads as "unchanged".

## Tests first

This story has no pre-fix failing test; the harness is the deliverable, and a
harness that runs and prints numbers is the test. Write it in this order.

### How the harness stays out of the default gate and how it is run

Both files are named `*.measure.spec.ts`, so they are inside the existing
`lib/**/*.spec.ts` include (they type-check under `tsconfig.spec.json` and are
excluded from the library build by `tsconfig.lib.json`'s `src/**/*.spec.ts`
exclude). Each wraps its suite in
`describe.skipIf(!process.env['NGKIT_MEASURE'])`. Without the variable the
default `task test` loads them, reports them as skipped, and runs nothing; no
generated or config file is edited. (`process` has no ambient types in this
project, so declare the one shape you use at the top of the file:
`declare const process: { env: Record<string, string | undefined>; memoryUsage(): { heapUsed: number; rss: number } };`.)

Run command, from the repository root (verified at `48e181a` with a scratch
spec: `gc` is exposed in the test worker, `WeakRef` exists, and `console.log`
appears with the verbose reporter):

```sh
unset NX_WORKSPACE_ROOT_PATH
NGKIT_MEASURE=1 NODE_OPTIONS=--expose-gc pnpm nx test ng-bootstrap \
  --include='lib/measure/*.measure.spec.ts' --coverage=false \
  --reporters=verbose --skip-nx-cache --output-style=static
```

`--skip-nx-cache` is required: `NGKIT_MEASURE` is not part of the Nx cache key,
so a cached run would print nothing new. `--coverage=false` avoids the target's
35% coverage threshold applying to a filtered run. Print every measurement as
one `console.log('MEASURE ' + JSON.stringify({...}))` line so it can be pasted
into the Result and grepped.

Assert only sanity (for example: counts are non-negative, the instances were
created); a measurement run never fails on a number.

### Measurement design

Subject: the table (`TableComponent`) and form (`FormComponent`) option objects,
resolved through `ConfigurableComponent`/`ConfigurerService`. Use `TestBed` with
a small host component that binds `[options]` so the real signal input, computed
and `configureOptions` path runs (as `table.component.spec.ts` does); set
`autoRender: false` on the table so the jQuery plugin is not part of the option
measurement.

1. **Sizes** (state them in the Result with the reason). Build option objects
   programmatically at three sizes per widget:

    | Size | Table | Form | Why |
    | -- | -- | -- | -- |
    | S | 5 columns, 2 toolbar buttons (about 40 leaf keys with defaults) | 4 controls | the common screen; the floor |
    | M | 20 columns, 6 buttons (about 150 leaf keys) | 15 controls | the demo and CRUD screens |
    | L | 80 columns, 20 buttons (about 500 leaf keys) | 60 controls | a deliberately large stress point, not a typical screen |

    Include nested objects (`icons`, `columns[i].formatter` callbacks, `pageList`
    arrays) so the diff recurses and skips functions as it does in production.
    Record the actual leaf count of each fixture.

1. **Workloads** (each at S, M, L; table and form):

    - **W1 repeated reads:** 10,000 reads of `component.config` with nothing
      changed (the computed's memoized path).
    - **W2 input churn:** 1,000 changes of the `[options]` input, in two
      variants: new identity with identical content, and new identity with one
      leaf changed.
    - **W3 override updates:** 1,000 each of `updateOptions` and `mergeOptions`
      (one variant with unchanged content, one with one changed leaf, one with
      an array replaced), then `clearOverrides`.
    - **W4 fresh-object binding (the CRUD pattern):** the host binds
      `[options]="build()"`, where `build()` returns a new equal object on
      every evaluation (as `addUpdateFormOptions()` and `deleteModalOptions()`
      do, with a new callback closure each time), over 1,000
      `fixture.detectChanges()` passes. Also run the memoized-binding variant
      (as `tableOptions()` does) for contrast.
    - **W5 mount/destroy churn:** create and destroy 50 and then 500 instances
      per widget size (with a live `ConfigurerService`, one `TestBed` per batch
      so the root service persists across the batch), once with options and
      once without.

1. **Operation counts** (count file; no timing taken from it). Per workload,
   record: top-level and total calls to `ObjectUtil.diff` (spy with
   `vi.spyOn(ObjectUtil, 'diff')`; the recursion calls it through
   `ObjectUtil.diff`, so the spy counts nested calls; track depth in a
   pass-through wrapper to separate top-level from total), calls to lodash
   `merge` and `mergeWith` (an ES module namespace cannot be spied, so
   `vi.mock('lodash-es', ...)` re-exporting wrapped pass-through
   `merge`/`mergeWith`), calls of `ConfigurerService.componentOptions` (spy),
   `componentDefaults` cache misses, and `configureOptions` calls (spy on the
   component's override). Report counts per read, per change and per destroy
   as well as totals.

1. **Time and memory** (time file; no spies, no `vi.mock`). For each workload
   and size: one discarded warm-up run, then 7 measured runs; use
   `performance.now()`; report median, min and max in milliseconds and per
   operation. Memory: call `gc()` (present because of `--expose-gc`; skip with
   a printed note if it is not a function) before and after each run; record
   `process.memoryUsage().heapUsed` after the pre-run gc, the peak of samples
   taken every 100 iterations, and after the post-run gc, with the retained
   delta; record `rss` once per workload.

1. **Retained instances.** In W5, hold a `WeakRef` to each destroyed component,
   call `gc()` (twice, with an awaited macrotask between), and count the refs
   still alive. Also read the service's per-instance cache sizes after
   destruction (`Object.keys` of the private `inputsCache`, `overridesCache`,
   `finalOptionsCache` through a typed cast to a local interface in the
   harness; this reads private state, which a harness may do, and must not be
   copied into product tests). A destroyed instance with a surviving cache
   entry or a live `WeakRef` is a finding to report, not to fix.

1. **Criteria options for the owner.** After the numbers, write in the Result,
   per workload W1 to W5, two or three candidate criteria as options, each
   stated as a measurable threshold against this baseline, for example
   "operation counts no higher than baseline for every size", "median time per
   operation within +10% at S and M", "improvement of at least X% in total
   `diff` calls in W4", "heap delta after gc no higher", "zero surviving
   references after churn". Say which criteria the recorded noise (the spread
   across the 7 runs) can support and which it cannot. Do not select one: mark
   the choice `Owner decides`.

1. **Environment.** Record, from the shell, the output of `node -v`,
   `uname -srm`, the CPU model (`sysctl -n machdep.cpu.brand_string` on
   macOS), the installed versions of `vitest`, `@angular/core`, `lodash-es`,
   whether `gc` was exposed, the run command, the commit, the date, and
   whether the machine was otherwise idle.

### CRUD-manager analysis (written in `## Result`, no code)

Verify the responsibility table in "Current behaviour" against the code and the
spec and correct it. Then, for each seam you can name (for example: permissions
and features; table-options assembly; form-to-request conversion and the
idempotency key; save-error mapping; import/export; delete flow; the widget
binding in `init`/`bindTable`):

- the state that crosses the seam (fields and signals, including what a
  `CrudContext` member is used for);
- duplicated policy at or across it (for example the two error-detail formatters
  at `:640-642` and `:667-669`, repeated `alert` plus `updateCurrentMode`
  sequences, the `takeUntilDestroyed` subscribe/error pattern repeated through
  the file);
- whether the logic is presentation-free (candidate for `libs/ng/crud`) or tied
  to dialogs and widgets (stays in `libs/ng-bootstrap/crud`), citing ADR-0002;
- a recommendation per seam: `split` (coupling or duplicated policy falls, and
  say what falls), `keep` (extraction would only move code), or
  `defer until S19.6.1 lands`, each with the evidence. Count, for each
  proposed split, the fields that would have to be passed or shared, and the
  private members the existing spec would have to reach differently. Make no
  performance claim here.

Also measure one thing for the CRUD side, using the same harness: how many times
`addUpdateFormOptions()` and `deleteModalOptions()` run, and how many
`componentOptions` calls and `merge` calls they cause, over 1,000 change
detection passes of a rendered `CrudComponent` (reuse the fake data source and
fixtures from `crud.component.spec.ts` if usable; if not, say why and use W4).
