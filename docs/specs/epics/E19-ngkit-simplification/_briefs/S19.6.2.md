# S19.6.2 — Apply configuration changes with the same control names

Brief for
[S19.6.2](../F19.6-forms-and-crud.md#s1962-apply-configuration-changes-with-the-same-control-names),
at `bfd1392`.

## Goal

Make `FormComponent` apply a changed group-level `validators` option and a
changed `contextParams` to the existing form group when the control names are
unchanged, keep value, touched, dirty and disabled state across those and other
non-structural option changes, and decide a group rebuild by the set of control
names compared exactly (not as a comma-joined string), so a rebuild happens
exactly when the names change.

## Settled

- The story's acceptance (F19.6, S19.6.2) and the epic's Scope constraints: keep
  public imports and wire formats; no dependency; no change to a shared
  utility that other components use (see `ObjectUtil.diff` below).
- F19.3 S19.3.1 (closed): each correctness case gets a failing pre-fix
  regression through the rendered host, then a passing post-fix run.
- **Rebuild rule (reviewer ruling, 2026-11-18; derived from the acceptance and
  today's behaviour, no consumer-visible trade-off):**
    1. A change to the **set of control names** (a control added, removed or
       renamed; order is irrelevant) rebuilds the group. The new group holds the
       new definitions' default values and is pristine, untouched and enabled;
       values, touched, dirty and disabled state of the old group are discarded.
       Today's code already does exactly this (`form.component.ts:90-106`); only
       the comparison is corrected. `disabledFields` is applied by `enable()`,
       `reset()` and `update()` as today, not by the rebuild.
    1. **Any other option change is applied in place** to the existing group and
       keeps value, touched, dirty and disabled state: cosmetic options
       (`header`, `classes`, `layout`, buttons, `htmlAttributes`) need no group
       work; a changed `validators.validateDateRange` is set on the group with
       `setValidators` and re-evaluated with `updateValueAndValidity`; changed
       `contextParams` produce a new `context` object around the same group.
    1. A **same-name control-definition change** (a different default, a swapped
       `FormControl`, a different control-level validator, a different control
       kind) is **not applied**: the existing control keeps its value,
       validators and state. This is today's behaviour; it is documented, not
       changed. A consumer that needs a new definition renames the control or
       recreates the form. Reason: the options layer cannot see control-level
       validators (the shared `ObjectUtil.diff` skips function values by design,
       `libs/ng/core/src/lib/core.utils.ts:218-220`, so `config` does not change
       when only array-definition validators change) and `CrudManager` re-creates
       its controls on every change detection (`crud.manager.ts:378-383`, bound
       at `crud.component.html:97`), so re-applying definitions would reset or
       re-validate the CRUD form continually. Control-level validators are
       therefore out of the meaning of "replacing validators" here: that option
       is `FormOptions.validators`.
- "Delimiter-containing names" means a control name containing the `,` that the
  current comparison joins names with. Names containing `.` already work
  (`formGroup.controls['a.b']`, which is how `FormFieldComponent` resolves a
  control, `form-field.component.ts:113`); keep that.

## Current behaviour

Line numbers at `bfd1392`, in
`libs/ng-bootstrap/form/src/lib/form/form.component.ts`. Observed with a scratch
spec through a rendered host with a signal-driven `[options]` (deleted).

- **The group is built once per name set.** The constructor effect (`:85-107`)
  sorts `Object.keys(config.controls)`, joins them with `,` (`:87-89`), and
  returns early when the string equals `_lastControlKeys` (`:90-92`). Only on
  a different string does it build `formBuilder.group(...)` (`:98-103`) and
  `_context` (`:104-106`). The group-level `validateDateRange` validator
  (`:97`, `:100-102`) and `contextParams` (`:105`) are read only inside that
  rebuild.
- **(a) Replacing validators, same names: no effect.** Observed: the group
  instance is unchanged after (i) removing a control-level
  `Validators.required` from an array definition (still invalid), (ii)
  swapping a `FormControl('', Validators.required)` for `FormControl('')`
  (still invalid, same group), and (iii) adding `validators.validateDateRange`
  (same group; nothing attaches the validator because `:97-103` is
  unreachable). Also observed: with array definitions, changing only a
  validator (`Validators.required` to `Validators.email`, or
  `TEXT({minLength: 2})` to `TEXT({minLength: 5})`) leaves `config.controls`
  the same reference, because `ObjectUtil.diff` ignores functions; with
  `FormControl` instances the config does change but the effect still returns
  at `:90-92`.
- **(b) Changing context, same names: no effect.** Observed: after changing
  `contextParams` from `{x: 1}` to `{x: 2}`, `config.contextParams.x` is `2`
  while `form.context` is the same object and `context.$implicit.x` is still
  `1` (`:104-106` not reached).
- **(c) Changing control definitions.** Observed: add, remove and rename each
  create a new group holding exactly the new names; the old values are gone.
  Same names with a different default or type (`c: ['2']` to `c: [5]`): same
  group, value still `'2'`. Reordering the same names: same group (sorted
  comparison).
- **(d) Delimiter.** Observed: `{ 'a,b': [''] }` then `{ a: [''], b: [''] }`:
  both join to `'a,b'`, so the group is **not rebuilt** and still has the
  single control `a,b`, which is wrong for the new definitions. A name
  containing `.` works: `controls['a.b']` is found; `formGroup.get('a.b')` is
  not (it splits on `.`), and nothing in the form components calls `get` with
  a user name.
- **(e) Cosmetic changes do not discard edits today.** Observed: with a value
  edited, `markAsDirty`/`markAsTouched` set and a field enabled that
  `disabledFields` lists, changing `header` and `classes` keeps the same
  group, the edited value, dirty and touched, and the enabled field; a
  header-only change keeps the edited value; after `form.disable()` a cosmetic
  change keeps it disabled; `CrudManager` calls `updateOptions({ header })`
  while the form is being edited (`crud.manager.ts:390`, `:408`). Adding
  `disabledFields` later does not disable anything until `enable()`, `reset()`
  or `update()` runs (`:166-171`). These pass today and must keep passing:
  they pin the "do not discard" half of the acceptance.
- **A rebuild does not touch `_updateFlag`.** `_updateFlag` (`:76`, `:154`,
  `:161`) is not touched by a rebuild; left alone (Out of scope).

## Change

- **Change:** `libs/ng-bootstrap/form/src/lib/form/form.component.ts`, the
  constructor effect and the `_lastControlKeys` field only:
    1. Replace the `string` key with the sorted array of control names, compared
       element by element (for example `string[] | undefined`, equal when the
       lengths match and every element is `===`); no delimiter. Keep the
       `localeCompare` sort and the debug line with the names.
    1. When the name set differs (or on the first run), rebuild exactly as now
       (`formBuilder.group(controls, ...)` with the `validateDateRange` group
       validator, then `_context`).
    1. When the name set is unchanged and a group exists, apply in place: set the
       group validator from the current `config.validators?.validateDateRange`
       (`FormUtil.VALIDATORS.DATE_RANGE(...dateRange)`, or `null` when absent)
       with `setValidators`, then
       `updateValueAndValidity({ emitEvent: false })`; and replace `_context`
       with a new object around the same `_formGroup` and the current
       `contextParams`, as `:104-106` builds it. Do both only when the value
       actually changed (compare the `validateDateRange` array element-wise;
       compare `contextParams` with lodash `isEqual`), so an unchanged options
       object re-supplied on every change detection (as `CrudManager` does) is a
       no-op.
    1. Write the rule from Settled as the doc comment on the effect (or a short
       `@remarks` on `FormComponent`): rebuild on a name-set change with reset
       semantics; everything else in place; same-name definition changes are not
       applied.
- **Change:** `libs/ng-bootstrap/form/src/lib/form/form.component.spec.ts`: the
  tests below.
- **Change (docs):** if a page under `docs/` documents `FormComponent` options
  (search `rnf-form`, `validateDateRange`, `contextParams`), add the rule
  there in one short paragraph; otherwise no doc change.
- **Leave alone:** `ConfigurableComponent`, `ConfigurerService`,
  `ObjectUtil.diff` and any other shared options code (the function-skipping
  diff is deliberate); `reset`, `update`, `enable`, `disable` and
  `_updateFlag`; `disabledFields` handling; the field components under
  `form/fields/`, in particular multi-typeahead, which S19.6.3 just changed;
  `CrudManager`, `CrudComponent`, `UserSettingsComponent` and their option
  builders; `FormUtil`; stories.

## Tests first

All in `form.component.spec.ts`, in a new
`describe('FormComponent configuration changes')`, through a small standalone
host component declared in the spec:
`<rnf-form [options]="opts()" [template]="tpl" />` with `opts` a
`signal<Partial<FormOptions>>`, an `<ng-template #tpl let-ctx>` that renders a
`contextParams` value (for example `{{ ctx.label }}`), and
`viewChild(FormComponent)`. Drive changes with `opts.set(...)` and
`fixture.detectChanges()`. Do not call the component's internals. Write them
first and run them against the unchanged component; the ones marked "fails
before" must fail for the stated reason, then pass after the change. Run each
failing test alone (`-t '<name>'`) to confirm it fails by itself.

- **`applies a replaced group validator with the same control names`**: controls
  `{ start: [''], end: [''] }`, then set the same controls plus
  `validators: { validateDateRange: ['start', 'end'] }`; set `start` to
  `2026-12-31` and `end` to `2026-01-01`; assert `form.errors` has `dateRange`
  and the group instance is the same as before the change. Then remove
  `validators`; assert `form.errors` is `null`. Fails before: no error (the
  validator is never attached).
- **`renders changed context params with the same control names`**: set
  `contextParams: { label: 'one' }`, assert the rendered text, set
  `{ label: 'two' }` with the same controls, assert the rendered text is `two`
  and `form.formGroup` is the same instance. Fails before: still `one`.
- **`keeps edits, touched, dirty and disabled state on a cosmetic change`**:
  controls `{ a: ['x'], b: ['y'] }`, `disabledFields: ['b']`, `header: 'H1'`;
  call `form.enable()`; set `a` to `edited`, `markAsDirty`, `markAsTouched` on
  `a`; disable `b` through `form.controls['b'].disable()`; then change
  `header` and `classes`; assert same group instance, `a` still `edited`, `a`
  dirty and touched, `b` disabled, and the rendered `<h5>` shows the new
  header. Passes before (pins the kept behaviour).
- **`keeps a disabled form disabled on a cosmetic change`**: `form.disable()`,
  change `header`; assert `form.disabled`. Passes before.
- **`keeps edits when only validators and context change`**: edit `a`, mark it
  dirty and touched, then change `validators` and `contextParams` with the
  same names; assert same group, value, dirty and touched kept. Fails before
  only for the validator and context assertions of the two tests above; this
  one pins state across the new in-place path and must pass after.
- **`does not re-apply an unchanged options object`**: spy on the group's
  `setValidators` (`jest`/`vitest` `spyOn` on the instance, matching the
  spec's runner) and on `updateValueAndValidity`; re-set an equal but newly
  created options object (including a new `validators` array and new
  `contextParams` object) and run change detection several times; assert zero
  calls and the same `form.context` object. Passes before (nothing is
  applied); guards the `CrudManager` pattern.
- **`rebuilds the group and resets values when a control is added, removed or renamed`**:
  three steps from `{ a: ['x'] }` with `a` edited: add `b` (assert new group,
  keys `a`,`b`, `a` back to `x`, pristine), remove `a`, rename `b` to `c` (new
  group each time, exactly the new keys). Passes before (pins today's rebuild
  and its reset semantics).
- **`does not rebuild when the names are only reordered`**: `{ z, y }` then
  `{ y, z }`; same group, edit kept. Passes before.
- **`keeps the control and its value when a same-name definition changes`**:
  `{ c: ['2'] }`, then `{ c: [5] }`; assert same group and value `'2'`. Passes
  before (documents the settled "not applied" rule).
- **`rebuilds when names containing a comma change to separate names`**:
  `{ 'a,b': [''] }` then `{ a: [''], b: [''] }`; assert a new group whose keys
  are `['a', 'b']`, and the reverse direction. Fails before: same group with
  the single control `a,b`.
- **`resolves a control name containing a dot`**: controls `{ 'a.b': ['x'] }`;
  assert `form.controls['a.b'].value` is `x`, the group is built once across a
  cosmetic change, and a name change rebuilds it. Passes before.

## Out of scope

- Applying a changed default, `FormControl` instance, control-level validator or
  control kind to an existing same-name control; changing `ObjectUtil.diff`,
  the options resolver or `ConfigurerService`.
- Applying a changed `disabledFields` in place, applying `disabledFields` on a
  rebuild, or changing `_updateFlag` (including its value after a rebuild).
- Changing option builders in `CrudManager` or `UserSettingsComponent`, or any
  field component.
- Making `formGroup.get('a.b')` work, or changing how names are resolved.
- Adding an option, input or method to `FormComponent`.
- A new decision about reset semantics: the rule in Settled is the rule; a
  better one is a separate story.
