# F11.2 — `@rn-forge/nx-plugin`

**Status:** planned · **Owner:** ngkit · **Epic:** [E11](index.md)

Published Nx plugin for generic workspace, repo, and project scaffolding. It contains no Angular-specific setup and does not depend on `@rn-forge/ng-plugin`. It ships in the fixed release group ([design](design.md#release-model)).

## Design

### Decisions

Recorded by S11.2.7 (owner decision, 2026-10-17).

- **`setup-release` writes ngkit's own model.** Fixed (grouped) versioning, `release.projects: ["tag:publishable"]`, tarballs on GitHub Releases, npm disabled. The CI template supports only one fixed group with `v{version}` tags ([CI template](../../../architecture/ci-template.md#assumptions)), so the `mode` option and independent versioning are not offered. The registry option is dropped with npm.
- **`create-publishable-lib` is framework-neutral.** It scaffolds a JS library, tags it `publishable` and applies the release metadata; Angular library scaffolding is [`ng-plugin:create-library`](F11.1-ng-plugin.md), which composes this generator.
- **GitHub only in v1.** `setup-ci`'s `provider` enum is `github`; `setup-release`'s `ciProvider` is `github | none`. Azure DevOps has no template here to copy or test.
- **pnpm is pinned through Corepack** and the `packageManager` field, as the template's setup action reads it.
- **`setup-agentic-coding` is deferred** (S11.2.6), with entry criteria.

### Considered and rejected

- **Independent versions as the default.** Consumers of a generated workspace would need a compatibility matrix, which [ADR-0003](../../../adr/ADR-0003.md) rejects for ngkit's own libraries; the CI template also fails a release when `HEAD` carries more than one `v*` tag.
- **Azure DevOps templates from day one.** Nothing in this repository can test them.
- **Keeping Angular scaffolding in `nx-plugin` behind `--framework=angular`.** It breaks the one-way dependency rule in [design.md](design.md#design-decision).

### `setup-workspace`

Configures an existing Nx workspace with rn-forge repo-level standards.

#### Usage

```bash
pnpm nx g @rn-forge/nx-plugin:setup-workspace
```

#### Schema

| Option                   | Type    | Required | Default | Description                                    |
| ------------------------ | ------- | -------- | ------- | ---------------------------------------------- |
| `packageManager`         | enum    | no       | `pnpm`  | `pnpm \| npm \| yarn`                          |
| `skipInstall`            | boolean | no       | `false` | Skip dependency installation                   |
| `configureTsConfig`      | boolean | no       | `true`  | Patch root TypeScript defaults                 |
| `configureWorkspaceFile` | boolean | no       | `true`  | Ensure workspace package manager config exists |

#### Steps

1. Install repo-level dev dependencies.
2. Patch `tsconfig.base.json`:
   - `target: ES2022`
   - `lib: [ES2022, DOM]`
   - `module: esnext`
   - `moduleResolution: bundler`
3. Add `pnpm-workspace.yaml` from template if missing and package manager is `pnpm`.
4. Add or patch root formatting/linting baseline.
5. Format files.
6. Install packages unless skipped.

### `create-publishable-lib`

Scaffolds a framework-neutral publishable library following the [publishable-library guide](../../../guides/development.md#adding-a-publishable-library). Angular libraries use `@rn-forge/ng-plugin:create-library`, which runs this generator for the shared part.

#### Usage

```bash
pnpm nx g @rn-forge/nx-plugin:create-publishable-lib --name=my-lib --importPath=@acme/my-lib
```

#### Schema

| Option              | Type    | Required | Default | Description                                                                           |
| ------------------- | ------- | -------- | ------- | ------------------------------------------------------------------------------------- |
| `name`              | string  | yes      | —       | Library project name                                                                  |
| `importPath`        | string  | yes      | —       | Package name                                                                          |
| `directory`         | string  | no       | `libs/` | Library directory                                                                     |
| `coverageThreshold` | number  | no       | `35`    | Coverage threshold                                                                    |
| `skipInstall`       | boolean | no       | `false` | Skip dependency installation                                                          |
| `skipScaffold`      | boolean | no       | `false` | Apply only the publishable settings to an existing project (used by `create-library`) |

#### Steps

1. Validate that the project name is free (unless `skipScaffold`).
2. Generate a JS library with `@nx/js:library` (publishable, strict).
3. Write package metadata: `description`, `license`, `repository`, `publishConfig.access: "public"`.
4. Tag the project `publishable`; set `release.version.manifestRootsToUpdate`; declare `pack`, `verify-dist` and `nx-release-publish` with `dryRun: true`.
5. Apply the coverage threshold.
6. Format files; install unless skipped.

The generator never edits `nx.json#release.projects`; the tag is what joins a release.

### `setup-ci`

Adds repo-level CI workflows.

#### Usage

```bash
pnpm nx g @rn-forge/nx-plugin:setup-ci --provider=github
```

#### Schema

| Option     | Type    | Required | Default  | Description                     |
| ---------- | ------- | -------- | -------- | ------------------------------- |
| `provider` | enum    | no       | `github` | `github`                        |
| `force`    | boolean | no       | `false`  | Replace existing workflow files |

#### Steps

1. Write the CI template files listed under [Template-owned files](../../../architecture/ci-template.md#template-owned-files) that `ci.yml` uses, skipping any that exist and differ unless `force`.
2. Ensure `package.json#packageManager` pins the package manager (Corepack) and `.nvmrc` exists; the setup action reads both.
3. Format files.

The generator writes the template unchanged. Repository-owned declarations (targets, `nxCloudId`, Sonar properties, secrets) are listed in the same page and are the user's to supply; the generator prints the ones it did not find.

### `setup-release`

Configures fixed Nx release with GitHub Release tarballs, the model described in [ADR-0003](../../../adr/ADR-0003.md).

#### Usage

```bash
pnpm nx g @rn-forge/nx-plugin:setup-release
```

#### Schema

| Option       | Type    | Required | Default  | Description                     |
| ------------ | ------- | -------- | -------- | ------------------------------- |
| `ciProvider` | enum    | no       | `github` | `github \| none`                |
| `force`      | boolean | no       | `false`  | Replace existing release config |

#### Steps

1. Patch `nx.json#release`: `projects: ["tag:publishable"]`, `version.preVersionCommand`, `changelog.workspaceChangelog.createRelease: false`.
2. Ensure `pack` and `verify-dist` target defaults exist in `nx.json#targetDefaults`.
3. Write `.github/workflows/release.yml` and the `tools/ci` scripts it uses when `ciProvider=github`.
4. Format files.

Publishable projects are not listed; they join by carrying the `publishable` tag. The generator keeps npm publishing disabled (`dryRun: true`).

### `setup-boundaries`

Configures project tags and module boundary enforcement.

#### Usage

```bash
pnpm nx g @rn-forge/nx-plugin:setup-boundaries
```

#### Schema

| Option                    | Type    | Required | Default               | Description                      |
| ------------------------- | ------- | -------- | --------------------- | -------------------------------- |
| `tagModel`                | enum    | no       | `type-scope-platform` | Boundary tagging model           |
| `applyToExistingProjects` | boolean | no       | `false`               | Attempt to tag existing projects |
| `force`                   | boolean | no       | `false`               | Replace existing boundary config |

#### Steps

1. Add standard tag taxonomy documentation.
2. Patch eslint module-boundary rules.
3. Optionally apply tags to existing projects using best-effort inference.
4. Format files.

## Design defaults

These defaults stand until a story's work shows a reason to change them.

| Topic               | Default                                                                                        |
| ------------------- | ---------------------------------------------------------------------------------------------- |
| Package managers    | Schema open, pnpm implemented first                                                            |
| Existing tsconfig   | Merge only; preserve explicit settings                                                         |
| Workspace type      | Package-based and integrated; validate behavior separately                                     |
| Storybook           | Not installed by `setup-workspace`; a flag on the library generators                           |
| Test commands in CI | Affected by default (the template)                                                             |
| Tag taxonomy        | `type:*`, `scope:*`, `platform:*`; existing projects reported, not tagged                      |
| Enforcement         | Error in CI, local lint default behavior; `scope:shared`, `type:util` for shared code          |
| Template files      | Non-TS assets: whether the package needs `patch-package-exports` is checked when it is created |
