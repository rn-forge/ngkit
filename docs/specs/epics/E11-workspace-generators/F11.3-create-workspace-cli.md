# F11.3 — `create-rn-forge-ng-workspace` CLI

**Status:** planned · **Owner:** ngkit · **Epic:** [E11](index.md) · **Release:** [Release 2](../../../releases/release-2/index.md)

**Depends on:** [F11.1](F11.1-ng-plugin.md) (S11.1.1) and [F11.2](F11.2-nx-plugin.md) (S11.2.1), the generators it runs.

Thin wrapper around `create-nx-workspace` that then installs and invokes the plugin generators. All workspace wiring logic lives in the plugins; the CLI only handles greenfield workspace creation and orchestration.

## Stories

### S11.3.1 — Greenfield workspace CLI

**Status:** planned

**Acceptance:**

```gherkin
Feature: create-rn-forge-ng-workspace CLI

  Scenario: interactive greenfield
    Given no workspace exists at the target path
    When I run "pnpm dlx create-rn-forge-ng-workspace@latest"
    And I enter "my-workspace" and "shell"
    Then a valid Nx workspace is created at my-workspace/
    And @rn-forge/nx-plugin:setup-workspace has run
    And @rn-forge/ng-plugin:setup has run for "shell"
    And "pnpm nx serve shell" starts the app without errors

  Scenario: non-interactive via flags
    When I run "pnpm dlx create-rn-forge-ng-workspace@latest --name=acme --appName=portal --yes"
    Then the workspace is created without prompts

  Scenario: invalid workspace name rejected before any commands run
    When I run "pnpm dlx create-rn-forge-ng-workspace@latest --name='My App'"
    Then the CLI exits with a validation error
    And no create-nx-workspace command ran

  Scenario: step failure prints recovery commands
    Given create-nx-workspace succeeds
    But @rn-forge/ng-plugin:setup exits non-zero
    Then the CLI prints the remaining manual steps and exits non-zero

  Scenario: pinned versions
    When the CLI installs the plugins
    Then it installs @rn-forge/ng-plugin and @rn-forge/nx-plugin at exactly the CLI's own version

  Scenario: package manager pinned
    Then the generated workspace's package.json packageManager names the pnpm version in use

  Scenario: pnpm outside the tested range
    Given the detected pnpm major is not in the tested range
    When I run the CLI
    Then it prints a warning naming the detected version and continues
```

The tests run the CLI's steps against a stub runner in this repository (command lines and order asserted); the end-to-end scenarios with `create-nx-workspace` run in a temporary directory.

### S11.3.2 — Decide the CLI's versioning and pnpm policy

**Status:** done (2026-10-17)

**Acceptance:** this feature's Design records the decisions and the rejected options.

## Design

### Decisions

Recorded by S11.3.2 (owner decision, 2026-10-17).

- **Fixed group, exact pins.** The CLI is tagged `publishable` and releases with `ng`, `ng-bootstrap` and both plugins ([design.md](design.md#release-model)). Its dependency on the plugins is an exact pin (a release rewrites it), and it installs the plugins at its own version, so one CLI version always yields one matched set.
- **pnpm.** The CLI detects the pnpm version, warns when it is outside the tested range and continues. It does not choose a different creation flow per version. The generated workspace pins `packageManager` through Corepack.
- **Name.** The package keeps the Angular-specific name `create-rn-forge-ng-workspace`.
- **Recovery.** On a step failure the CLI prints all remaining manual commands, not only the failed one.

### Considered and rejected

- **Installing `latest` plugins.** A CLI run could then pair a CLI with plugins it was never tested against.
- **A per-version pnpm flow.** No difference between pnpm versions is documented, so it would be speculative.

### CLI options

| Flag               | Prompt fallback     | Default         | Description                                |
| ------------------ | ------------------- | --------------- | ------------------------------------------ |
| `--name`           | `Workspace name?`   | —               | Workspace directory name                   |
| `--appName`        | `App name?`         | `app`           | Initial Angular application name           |
| `--directory`      | `Output directory?` | `process.cwd()` | Where to create the workspace              |
| `--packageManager` | `Package manager?`  | `pnpm`          | `pnpm \| npm \| yarn`                      |
| `--skipGit`        | flag only           | `false`         | Skip git init                              |
| `--skipNgSetup`    | flag only           | `false`         | Skip `@rn-forge/ng-plugin:setup`           |
| `--skipNxSetup`    | flag only           | `false`         | Skip `@rn-forge/nx-plugin:setup-workspace` |
| `--yes`            | flag only           | `false`         | Accept all defaults, no prompts            |

### Execution steps

1. Collect options, validate the workspace name and warn if the pnpm version is outside the tested range.
2. Run `create-nx-workspace` with the Angular monorepo preset.
3. Install `@rn-forge/nx-plugin` and `@rn-forge/ng-plugin` as dev dependencies, at the CLI's own version.
4. Run `@rn-forge/nx-plugin:setup-workspace` unless skipped.
5. Run `@rn-forge/ng-plugin:setup --project=<appName>` unless skipped.
6. Print success command: `cd <name> && pnpm nx serve <appName>`.

On any step failure, print remaining manual recovery commands.
