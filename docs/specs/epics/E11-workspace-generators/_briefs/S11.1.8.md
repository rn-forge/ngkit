# S11.1.8 — Peer-only packages resolve in the lockfile

Brief for
[S11.1.8](../F11.1-ng-plugin.md#s1118-peer-only-packages-resolve-in-the-lockfile),
at `b3fe3c3`.

## Goal

Stop pnpm's "has dependencies but does not have a modules directory" warning for
peer-only workspace packages, here and in the workspaces that use the plugin.
The plugin package lists its peers in `devDependencies` too, and
`create-library` writes every library's peers into its `devDependencies` as
well.

## Settled

- **Contract:** F11.1's Design, decision "Peers are also dev dependencies";
  S11.1.8's acceptance; S11.1.7's amended `create-library` step and acceptance
  line.
- **Plugin package:** `tools/ng-plugin/package.json` gains `devDependencies`
  equal to its `peerDependencies` (`@nx/angular` `^24.0.0`, `@nx/devkit`
  `^24.0.0`, `typescript` `^5.4.0 || ^6.0.0`), placed just before
  `peerDependencies`.
- **Lockfile:** after editing the manifest, run
  `pnpm install --no-frozen-lockfile` once (the one allowed non-`task`
  command; record it under Deviations). The reviewer observed that this writes
  exactly the 12-line `tools/ng-plugin` importer, with the three packages
  under `devDependencies`, and nothing else. Any other change to
  `pnpm-lock.yaml` stops the story. Do not use `--fix-lockfile`: it downgrades
  unrelated packages.
- **`create-library`:** in `movePeers`
  (`src/generators/create-library/generator.ts`), after the `@angular/*`
  entries are in `peerDependencies`, set `devDependencies[name] = range` for
  every `peerDependencies` entry not already in `devDependencies`; an existing
  `devDependencies` range is kept. `dependencies` still loses its `@angular/*`
  entries and is dropped when empty. The generator's doc comment and the
  README's `create-library` paragraph say so.
- **Guide:** `docs/guides/development.md`, "Adding a publishable library": add
  an item after the metadata item (item 1): a library lists each of its peers
  in `devDependencies` with the same range, as `ng-bootstrap` does, because
  pnpm writes no lockfile importer for a package whose only dependencies are
  peers; `create-library` does this itself.
- **Not changed:** `libs/ng`, `libs/ng-bootstrap`, `libs/ng-tailwind` manifests
  (each already has an importer), root `package.json`, `pnpm-workspace.yaml`,
  the other generators.

## Current behaviour

At `b3fe3c3`, observed by the reviewer:

- Every `pnpm exec` in this repository prints
  `[WARN] ... Workspace package @rn-forge/ng-plugin has dependencies but does not have a modules directory`,
  and `tools/ng-plugin/node_modules` does not exist. `pnpm-lock.yaml` has no
  `tools/ng-plugin` importer; neither `pnpm install --lockfile-only` nor
  `--no-frozen-lockfile` adds one while the package has only
  `peerDependencies`.
- `create-library` run against this repository writes `libs/my-ui/package.json`
  with `peerDependencies` (`@angular/common`, `@angular/core`) and no
  `devDependencies`; after `pnpm install` the lockfile has no `libs/my-ui`
  importer and pnpm prints the same warning for `@acme/my-ui`.
- With the peers also in `devDependencies`, `pnpm install` writes both
  importers, the warning is gone, `pnpm install --frozen-lockfile` and
  `pnpm audit --prod --audit-level moderate` pass.
- The `create-library` spec's first scenario asserts `@angular/common` is in no
  dependency object other than `peerDependencies`; it fails once the mirror is
  written and must change with it.
- `task validate` stops at `kiln:doctor`
  (`kiln.ref: 'feature/v1' names a branch`), which fails on the base too; see
  Validation.
