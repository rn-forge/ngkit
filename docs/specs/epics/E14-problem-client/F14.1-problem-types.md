# F14.1 — `Problem` and its helpers

**Status:** done · **Implemented:** 2026-10-24 · **Owner:** ngkit · **Epic:** [E14](index.md) · **Release:** [Release 2](../../../releases/release-2/index.md)

**Depends on:** none.

The RFC 9457 members as a type, and pure functions that read a problem from an `HttpErrorResponse`. All live in `@rn-forge/ng/core` and import no application type ([ADR-0004](../../../adr/ADR-0004.md)).

## Stories

### S14.1.1 — Decide that RFC 9457 members are typed here

**Status:** done (2026-10-24)

**Acceptance:**

- [ADR-0004](../../../adr/ADR-0004.md)'s Decision says: ngkit types the members RFC 9457 defines (`type`, `title`, `status`, `detail`, `instance`) and recognizes a problem by the `application/problem+json` media type. It gives no extension member a meaning in `core`, adds no error class and no interceptor, and leaves `HttpErrorResponse` unchanged. The one extension ngkit reads is `errors`, in `ng/crud`, for form mapping.
- The ADR's `## Background` records the change and why: the original ban was against a parallel client schema, and a published standard falls under [ADR-0001](../../../adr/ADR-0001.md) principle 1. It records the rejected `ApiError` class and interceptor, with the reason in [E14](index.md#design).
- `ng/crud`'s existing `ProblemDetails` is named in the ADR as the one prior instance, replaced by [S14.2.1](F14.2-crud-adoption.md#s1421--ngcrud-reads-problems-through-core).

### S14.1.2 — `Problem` and `problemOf`

**Status:** done (2026-10-24)

```ts
export interface ProblemMembers {
  readonly type?: string;
  readonly title?: string;
  readonly status?: number;
  readonly detail?: string;
  readonly instance?: string;
}
export type Problem<$Ext extends object = object> = ProblemMembers & $Ext & { readonly [member: string]: unknown };

export const PROBLEM_MEDIA_TYPE = 'application/problem+json';
/** The problem body of an `HttpErrorResponse`, or `undefined` when it is not one. */
export function problemOf<$Ext extends object = object>(error: unknown): Problem<$Ext> | undefined;
```

**Acceptance:**

- `Problem`, `ProblemMembers`, `PROBLEM_MEDIA_TYPE` and `problemOf` are exported from `@rn-forge/ng/core`.
- `problemOf` returns the body when `error` is an `HttpErrorResponse` whose `Content-Type` media type is `application/problem+json` (case-insensitive, parameters such as `charset` ignored) and whose body is a non-array object. It returns `undefined` for any other error, an `application/json` body, a string or `Blob` body, and a bare object that is not an `HttpErrorResponse`.
- A spec compiles `problemOf<{ errors: { pointer?: string; detail: string }[] }>(error)?.errors` without a cast.

### S14.1.3 — `problemMessage`

**Status:** done (2026-10-24)

```ts
/** `detail ?? title` of a problem; otherwise the fallback for an HTTP failure, or the error's own message. */
export function problemMessage(error: unknown, fallback?: (status: number) => string): string;
```

**Acceptance:**

- A problem gives its `detail`, else its `title`, else the fallback.
- A non-problem `HttpErrorResponse` (including `status` 0) gives `fallback(status)`; the default fallback is `` `Request failed (${status})` ``, and an application passes its own wording.
- Any other `Error` gives its `message`; anything else gives `String(error)`. It never throws.
- Specs cover: a 404 problem with `detail`; a 500 problem with only `title`; an `application/json` body with a `detail` member (not a problem: fallback); a plain-text 502; a network failure (`status` 0); a custom fallback; a plain `Error`; `undefined`.

### S14.1.4 — `problemTypeOf` and `hasProblemType`

**Status:** done (2026-10-24)

```ts
/** The problem `type` resolved against the response URL; `'about:blank'` when absent; `undefined` when not a problem. */
export function problemTypeOf(error: unknown): string | undefined;
/** Whether the problem's resolved `type` equals `type`, resolved against the same base. */
export function hasProblemType(error: unknown, type: string): boolean;

// A backend whose types are `/problems/<code>`:
if (hasProblemType(err, '/problems/file-missing')) { ... }
```

**Acceptance:**

- A relative `type` is resolved against the `HttpErrorResponse`'s `url` as RFC 9457 §3.1.1 and RFC 3986 prescribe, so `/problems/x` from `https://host/v1/tracks/1` resolves to `https://host/problems/x`; an absolute `type` is returned as given. An absent `type` is `about:blank` (RFC 9457 §4.2.1).
- `hasProblemType` resolves its argument against the same base, so a relative and an absolute spelling of one URI match; it is `false` for a non-problem.
- Neither throws: with no `url`, or a `type` that is not a valid URI reference, the raw strings are compared.
- Specs cover: relative and absolute `type`; absent `type`; no `url`; an invalid `type`; a non-problem error.
