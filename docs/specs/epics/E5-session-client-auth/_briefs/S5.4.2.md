# S5.4.2 — Acceptance run

Brief for [S5.4.2](../F5.4-auth-acceptance.md#s542-acceptance-run), at
`0101d85`.

## Goal

Add the browser acceptance suite for the session client against the backend
fixture, and fix the one client defect it exposes: the loop guard does not cover
a login started by `authGuard`, so a session cookie the browser never stores
sends the user back to the provider instead of to the error page.

## Settled

- **Contract:**
    - [Design](../design.md): the Client behaviour table, including the "Loop
      guard" row (a `401` within `loopGuardMs` of the return navigation goes to
      `errorPath` with `error=session_not_established`), and the
      `session_not_established` error code;
    - S5.4.1 (closed 2026-11-16): the fixture accounts `demo-admin` (every
      `demo.products.*` key) and `demo-reader` (`demo.products`, `.list`,
      `.read`), `apps/ng-demo-e2e/src/support/fixture.ts` (`signIn`,
      `xsrfHeaders`, `resetFixture`), and the Playwright projects Chromium and
      Firefox (WebKit is excluded there, with its reason).
- **"The login page" with one provider.** The fixture offers one navigating
  provider and no password provider, so `startLogin` skips `loginPath` and
  goes straight to the provider (`/auth/login/development?return_to=<path>`),
  which renders its account list. Wherever the acceptance says a login starts
  or logout "returns to the login page", the test asserts that URL, with its
  `return_to`.
- **Signing in from the account list.** The development provider's account links
  drop `return_to` (they point at `/auth/login/development?account=<id>`), so
  clicking one lands on `/`. That is the server library's markup, outside this
  repository. The anonymous-visit test therefore signs in by navigating to the
  provider URL it was sent to with `&account=demo-admin` appended, which is
  the `?account=` sign-in the acceptance names. Do not click the link, and do
  not change the fixture to work around it.
- **Loop guard fix (`libs/ng/auth`):**
    - `AuthService` takes over the return detection from `AuthErrorPolicy`: its
      constructor consumes `sessionStorage['rnf.auth.loginStartedAt']` and
      records the return time.
    - `startLogin(returnTo)` checks it first: within `loopGuardMs` of that return,
      it navigates to `errorPath` with
      `queryParams: { error: 'session_not_established' }` and starts no login.
      The check is one-shot: once it trips, the recorded return is cleared, so
      "try again" from the error page starts a login.
    - `AuthErrorPolicy`'s `401` branch no longer keeps its own `returnedAt`: it
      clears credentials, sets `loginPending` and calls `startLogin`, which now
      applies the guard. Concurrent `401`s still start one navigation.
    - No public API is added; the new state and check are private to
      `AuthService`.
    - Update the README paragraph at `libs/ng/auth/README.md:94-101` to say the
      guard applies to every login `startLogin` would start, whether from a
      `401` or from `authGuard`.
- **The suite:** a new `apps/ng-demo-e2e/src/auth.spec.ts`, run on both
  projects. Tests that change products call `resetFixture(page)` first. The
  cases:
    1. **Anonymous visit:** `page.goto('/products')` reaches
       `/auth/login/development?return_to=%2Fproducts`; navigating to that URL
       with `&account=demo-admin` lands on `/products` with the table rendered
       and the user menu showing the account.
    1. **Read-only UI:** after `signIn(page, 'demo-reader')`, the list shows no
       Add, Update or Delete button, while Export is absent or present exactly
       as `enableExport` gives for those keys (assert only the three).
    1. **Refused `PATCH`:** the reader's client is made to believe it may update
       by routing `GET /auth/session` and adding `demo.products.update` to the
       body's `permissions` (`page.route` with `route.fetch()`, then
       `route.fulfill({ response, json })`). The reader selects Widget A, opens
       Update, changes the name and clicks Submit. The `PATCH` is answered
       `403`, the page lands on `/forbidden`, and after `page.unroute` a
       `page.request.get('/auth/session')` is `200` (still signed in).
    1. **Session ended by the fixture:** signed in as `demo-admin`, the test ends
       the session server-side with
       `page.request.post('/auth/logout/all', { headers: await xsrfHeaders(page) })`
       (`200`), then clicks the Name column header. That list request is
       answered `401`, and the page goes to
       `/auth/login/development?return_to=%2Fproducts`.
    1. **Cookie never stored:** the test starts as in case 1, but routes the
       `?account=` request (a URL predicate:
       `pathname === '/auth/login/development' && searchParams.has('account')`):
       `route.fetch({ maxRedirects: 0 })`, then
       `page.context().clearCookies({ name: '__Host-session' })`, then
       `route.fulfill` with the fetched status and body and its headers minus
       every `set-cookie`. All three are needed: `route.fetch` stores the cookie
       in the context, and a fulfilled `Set-Cookie` would store it again. The
       page must end at `/login/error?error=session_not_established` and stay
       there (assert the URL again after a short wait, so a loop back to the
       provider fails the test).
    1. **Logout:** signed in as `demo-admin`, open the user menu (`rnf-user-menu`
       toggle) and click "Sign out". The page goes to
       `/auth/login/development?return_to=%2F`, and
       `page.request.get('/auth/session')` answers `401`.

## Current behaviour

At `0101d85`, observed with the fixture running (FastAPI, Chromium):

- Case 1 passes: the anonymous visit reaches the provider URL above, and the
  `&account=` navigation lands on `/products` with five rows.
- Case 2 passes: the reader's list toolbar has no Add, Update or Delete.
- Case 3 passes: the `PATCH` is answered `403`, the page lands on `/forbidden`,
  and `/auth/session` then answers `200`.
- Case 4 passes: after `/auth/logout/all` (`200`), the next list request leads
  to `/auth/login/development?return_to=%2Fproducts`.
- **Case 5 fails:** after the return, `/auth/session` answers `401`, the page
  goes `/products` → `/` → `/auth/login/development?return_to=%2Fproducts`,
  and `sessionStorage` holds a new `rnf.auth.loginStartedAt`. Cause:
  `authGuard` (`libs/ng/auth/src/lib/auth.guards.ts:13-24`) calls `startLogin`
  (`auth.services.ts:77-96`), which has no loop check; the only check is in
  `AuthErrorPolicy.handle` (`auth.interceptors.ts:66-78`), which sees API
  `401`s, and the session probe is not one of them.
- Case 6 passes: "Sign out" lands on `/auth/login/development?return_to=%2F`,
  and `/auth/session` then answers `401`.

So the cases other than 5 are regression tests written against working
behaviour. Case 5 and the unit tests below fail first.
