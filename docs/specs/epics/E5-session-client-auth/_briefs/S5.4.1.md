# S5.4.1 — Fixture auth

Brief for [S5.4.1](../F5.4-auth-acceptance.md#s541-fixture-auth), at `babbd32`.

## Goal

Both backend fixtures serve the session auth routes through their pinned server
library, with the development provider and two fixture accounts, and protect the
products routes by permission. `ng-demo`'s fixture build talks to the fixture's
real `/auth`, and the F4.3 products e2e suite signs in and still passes on both
fixtures. FastAPI becomes the default e2e backend.

## Settled

- **Contract:** [Design](../design.md) (the routes, the session body, CSRF) and
  the F5.4 page's Context and Design sections. The entry check there lists
  what each pinned tag answers; this story wires it, it does not re-decide it.
- **Pins** (resolution checked 2026-11-16: `uv lock` resolves these together):
    - `apps/ng-demo-api-fastapi/pyproject.toml`:
      `rn-forge-fastapi[transfer] @ git+https://github.com/rn-forge/pykit@rn-forge-fastapi-v0.4.1#subdirectory=packages/rn-forge-fastapi`
      and
      `rn-forge-sqlalchemy @ git+https://github.com/rn-forge/pykit@rn-forge-sqlalchemy-v0.2.3#subdirectory=packages/rn-forge-sqlalchemy`;
    - `apps/ng-demo-api/pyproject.toml`:
      `rn-forge-django[drf,transfer] @ git+https://github.com/rn-forge/pykit@rn-forge-django-v0.6.1#subdirectory=packages/rn-forge-django`;
    - regenerate each `uv.lock` with `uv lock --project apps/<fixture>`. This is
      the one direct `uv` call allowed, because the fixture's lock is the
      dependency this story changes.
- **Accounts** (development provider; the subject is the `?account=` value):
    - `demo-admin`, name "Demo Admin": every key the demo's mock session holds
      (`DEMO_SESSION.permissions` in
      `apps/ng-demo/src/app/shared/mock-api.interceptor.ts`) plus
      `demo.products.upload`, which the server's action map requires for import
      and the template download;
    - `demo-reader`, name "Demo Reader": `demo.products`, `demo.products.list` and
      `demo.products.read` only. `demo.products` is the client's route guard key
      (`permissionGuard('demo.products')`), not a resource action, so the reader
      can open the screen.
    - Roles: `admin` and `reader` respectively.
- **Shared account objects.** Each fixture gets its own module (Python, no
  shared package) holding the two account definitions and the three objects
  the library's `AuthRoutesConfig` takes:
    - an `AccountResolver` whose `resolve` accepts an identity from issuer
      `development` with one of the two subjects (returning the subject as the
      account ID) and raises `AccountRejected` otherwise; `lookup` returns the
      subject for those two, else `None`;
    - an `AuthorizationContextProvider` returning each account's fixed
      `AuthorizationContext` (active, its permission and role sets, and its
      current session version);
    - an `AccountStateWriter` keeping `active` and the session version in a
      process-memory dict, which the provider reads. The Django fixture uses the
      same three objects, not Django users or groups.
- **FastAPI wiring** (`serve.py`, `products.py`):
    - `AuthRoutesConfig(providers={"development": DevelopmentIdentityProvider(accounts, debug=True)}, accounts=…, contexts=…, account_state=…, problem_type_base="https://ng-demo.invalid/problems/", error_route="/login/error", trusted_origins=("http://localhost:4200",), debug=True)`;
    - the app gets `auth_router(config)` and `SessionMiddleware` with
      `sessions_for(config)`;
    - each products route takes
      `requires_permission(current_principal(), "demo.products", <action>)`,
      with the action from the library's `DEFAULT_PERMISSION_ACTION_MAP`: list
      (and the export, which is the list with a format) `list`, get `retrieve`,
      create `create`, PATCH `partial_update`, batch create `batch_create`,
      batch delete `batch_delete`, import `import_items`, template
      `import_template`. Routers from the library take it through
      `include_router(..., dependencies=[...])`;
    - the actor written to the audit fields becomes the principal's subject where
      the route has the principal; `ACTOR` stays for the seed and library-router
      paths that do not pass one;
    - `POST /api/_test/reset` takes no permission.
- **Django wiring** (`settings.py`, `urls.py`, `products/views.py`):
    - `rn_forge.django.auth` in `INSTALLED_APPS`; the library's session middleware
      and `CSRF_MIDDLEWARE` in `MIDDLEWARE`; `SESSION_SETTINGS` and
      `CSRF_SETTINGS` applied as the library documents;
      `RN_FORGE_DJANGO["AUTH"]["PROBLEM_TYPE_BASE"]` set to the same base as
      FastAPI;
    - `auth_urlpatterns(config, prefix="auth")` with the same providers, account
      objects, `error_route` and trusted origin, in debug;
    - DRF's default authentication becomes the library's session authentication;
      `ProductViewSet` takes `PermissionKeyPermission` with
      `permission_key = "demo.products"`; `ResetView` stays open (`AllowAny`, no
      authentication);
    - keep the problem-details exception handler.
    - Read the library module docstrings in the fixture's virtualenv for the exact
      setting names; the F5.4 Design names them.
- **CSRF and the reset hook.** The reset hook is not exempted from the
  middleware's CSRF check. The e2e suite reads the `XSRF-TOKEN` cookie and
  sends `X-XSRF-TOKEN` on it, as the Angular client does.
- **Demo:**
    - `apps/ng-demo/proxy.fixture.json` proxies `/auth` to `http://localhost:8100`
      as well as `/api`;
    - the environment gains `mockAuth: boolean`: `true` in `environment.ts`,
      `false` in `environment.fixture.ts`. The mock interceptor's four `/auth/`
      branches run only when `environment.mockAuth`. The default build and its
      unit tests are unchanged in behaviour. Update the `environment.ts`
      comment, which says auth is always mocked.
- **e2e:**
    - `playwright.config.mts`: `NG_DEMO_BACKEND` defaults to `fastapi`; update the
      doc comment. CI sets no `NG_DEMO_BACKEND`, so CI runs FastAPI.
    - A support module `apps/ng-demo-e2e/src/support/fixture.ts` exports
      `signIn(page, account)` (navigates to
      `/auth/login/development?account=<account>&return_to=/products` and waits
      for `/products`) and `resetFixture(page)` (`POST /api/_test/reset` through
      `page.request`, with `X-XSRF-TOKEN` from the context's `XSRF-TOKEN`
      cookie, after a `GET /auth/session` if no such cookie is set yet).
    - `products.spec.ts`'s `beforeEach` calls `signIn(page, 'demo-admin')` then
      `resetFixture(page)` before `gotoProducts`. No test body changes.
- **Browsers.** The session cookie is `__Host-` and `Secure`. Find which
  Playwright projects keep it on `http://localhost:4200`. A project that
  refuses it is excluded from the fixture run with a comment giving the reason
  (for example `testIgnore` on that project, or dropping it from `projects`),
  not served over HTTPS. Record the outcome per project in `## Result`.

## Current behaviour

At `babbd32`:

- Neither fixture has auth: the Django settings say "No auth" (DRF `AllowAny`,
  no authentication classes); FastAPI's `serve.py` mounts only the products
  router. `GET http://localhost:8100/auth/providers` answers `404` (a problem
  response) on both, so every test in the new spec below fails on its first
  auth request with `404`.
- `proxy.fixture.json` proxies `/api` only.
- `mock-api.interceptor.ts:233-262` answers `/auth/session`, `/auth/logout`,
  `/auth/providers` and `/auth/login/password` in every build, so the fixture
  build's session is the mock's `demo-admin`.
- `playwright.config.mts`: `NG_DEMO_BACKEND` defaults to `django`. The readiness
  URL `http://localhost:8100/api/products` keeps working after the change,
  because Playwright accepts a `401` as ready.
- `products.spec.ts` resets through the standalone `request` fixture with no
  cookies or header. Once the products routes require a session, every
  products test fails at `gotoProducts` (the list request answers `401`, so
  the demo starts a login and the table never renders) until `beforeEach`
  signs in.

## Tests first

Write `apps/ng-demo-e2e/src/auth-fixture.spec.ts` first. It talks to the fixture
directly at `http://localhost:8100` through Playwright's `request` fixture, and
handles cookies by hand (`maxRedirects: 0`, read `Set-Cookie`, send `Cookie`),
so it does not depend on how a cookie jar treats `Secure` on `http`. It needs no
browser, so run it under one project only (for example `test.skip` unless
`testInfo.project.name === 'chromium'`). Each test fails before the change with
`404` on its first auth request.

1. `GET /auth/providers` answers
   `[{ id: 'development', name: 'development', kind: 'development' }]` (assert
   `id` and `kind`).
1. Anonymous `GET /auth/session`: `401`, and an `XSRF-TOKEN` cookie is set.
1. For each account,
   `GET /auth/login/development?account=<id>&return_to=/products` answers
   `302` to `/products` and sets `__Host-session`; `GET /auth/session` with it
   answers `200` whose `subject` is the account and whose `permissions` are
   exactly the account's set.
1. Signed in as `demo-admin`, an unsafe request without `X-XSRF-TOKEN` is `403`
   `application/problem+json` whose `type` ends `csrf-failed`.
1. `demo-reader`: `GET /api/products` `200`; `PATCH /api/products/1` with
   `If-Match` and the header `403`. `demo-admin`: the same `PATCH` `200`.
1. Unauthenticated `GET /api/products`: `401`.
1. `POST /auth/logout` with the header: `200` `{ "redirect": null }`, then
   `/auth/session` with the old cookie is `401`.

Then add the `beforeEach` sign-in to `products.spec.ts`, and confirm the
products suite passes on both backends.
