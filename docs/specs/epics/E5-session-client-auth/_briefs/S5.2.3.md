# S5.2.3 — Error policy

Brief for [S5.2.3](../F5.2-auth-wrapper.md#s523-error-policy), at `995a2f2`.

## Goal

Add the session client's HTTP interceptor. It applies Design's policy for `401`
and `403` to API requests, retries once after a CSRF failure, and guards against
login loops. Wire it into `ng-demo`.

## Settled

- **The wire contract** is [Design](../design.md) (S5.1.2, 2026-11-14): the
  Client behaviour table, "Which requests the interceptor handles", and the
  CSRF section.

- **Consumers are migrated minimally (owner, 2026-11-15).**

- **Public surface** (reviewer). This is the contract:

    ```ts
    // auth.interceptors.ts
    export const authInterceptor: HttpInterceptorFn;
    // auth.services.ts — AuthService gains:
    /** Start a login for returnTo as Design's "anonymous user reaches a guarded route" row says. */
    startLogin(returnTo: string): void;
    /** Set anonymous credentials locally, without calling the backend. */
    clear(): void;
    ```

    Add an internal `AuthErrorPolicy` service
    (`@Injectable({ providedIn: 'root' })`) in `auth.interceptors.ts` to hold
    the policy's state. Do not export it from `src/index.ts`.

- **`startLogin(returnTo)`** calls `providers()`.

    - If exactly one provider has a navigating kind (`oidc`, `oauth2` or
      `development`) and there is no `password` provider, it calls
      `login(id, returnTo)`.
    - Otherwise, and also when `providers()` errors, it calls
      `Router.navigateByUrl` with `loginPath?returnTo=<returnTo>`. Build that
      URL with `router.createUrlTree([loginPath], { queryParams: { returnTo } })`.

- **Which requests are handled.** Strip the query string from `req.url`. The
  request is handled when the result equals an `apiUrls` entry or starts with
  that entry plus `/`, so `/api` matches `/api` and `/api/x` but not `/apix`.
  Absolute URLs never match. A request to `sessionUrl`, `providersUrl`,
  `passwordLoginUrl` or `logoutUrl` is never handled, even if it falls under
  `apiUrls`. Every other request goes through untouched, whatever its status.

- **All handling is on the RxJS error channel**: a `catchError` on
  `HttpErrorResponse`. The interceptor never sets an `Authorization` header
  and never inspects success events.

- **`401` from a handled request.** The error always reaches the caller after
  the action below.

    - **Loop guard:**
        - At startup, `AuthErrorPolicy`'s constructor reads `sessionStorage` key
          `rnf.auth.loginStartedAt`, which `login()` writes. If the key is
          present, the constructor removes it and records
          `returnedAt = Date.now()`.
        - `provideRnForgeAuth`'s app initializer must `inject(AuthErrorPolicy)`, so
          this happens at startup rather than at the first request.
        - A `401` within `loopGuardMs` of `returnedAt` navigates to
          `errorPath?error=session_not_established`, and starts no login.
    - **Otherwise,** when no login is pending, call `clear()` and then
      `startLogin(router.url)`.
    - **Pending login:** a login is pending from the moment a `401` is handled
      until credentials next become authenticated. While it is pending, further
      `401`s only reach the caller, so parallel `401`s start one navigation.

- **`403` whose problem `type` ends in `csrf-failed`.** The problem `type` is
  read from `error.error?.type`, a string.

    - Call `refresh()`, then retry the request once.
    - Angular's XSRF interceptor runs before app interceptors
      (`node_modules/@angular/common/fesm2022/_module-chunk.mjs:2045`), so the
      held request still carries the old token. For a method other than `GET`,
      `HEAD` or `OPTIONS`, the retry therefore sets the configured
      `xsrfHeaderName` from `inject(HttpXsrfTokenExtractor).getToken()`, when
      the token is non-null.
    - If the retry fails with another `csrf-failed`, that error reaches the caller
      with no further refetch.
    - If `refresh()` itself errors, the original `403` reaches the caller.

- **Any other `403` from a handled request.**

    - Refetch the session once. Parallel `403`s share one in-flight `refresh()`
      (`share()` on a held observable, cleared when it settles).
    - Then call `navigateByUrl(forbiddenPath)` once per shared refetch.
    - The error reaches the caller. A `403` never calls `clear()` or
      `startLogin()`.

- **Demo wiring:**
  `provideHttpClient(withInterceptors([authInterceptor, mockApiInterceptor]))`.
  `authInterceptor` comes first, so the mock's errors flow back through it.

## Current behaviour

At `995a2f2`:

- `libs/ng/auth/src/lib/auth.interceptors.ts` does not exist; S5.2.1 deleted the
  bearer-token interceptor. Nothing handles `401` or `403`, so a `401` from
  `/api` reaches the caller and nothing navigates.
- `auth.services.ts`:
    - `login()` writes `rnf.auth.loginStartedAt` and calls
      `FullPageNavigation.assign` (`auth.navigation.ts`, internal);
    - `providers()`, `logout()` and `refresh()` exist;
    - there is no `startLogin` or `clear`.
- `auth.providers.ts:87-97`: the app initializer awaits `refresh()` and injects
  nothing else.
- `apps/ng-demo/src/app/app.config.ts`:
  `withInterceptors([mockApiInterceptor])`.
- Docs say "An error-policy interceptor follows" at `libs/ng/auth/README.md:68`,
  `docs/guides/building-an-app.md:326` and
  `docs/guides/building-an-app.md:535`.
- `auth.source.spec.ts` fails if any file under `libs/ng/auth/src` contains
  `localStorage`, `jwt-decode` or `Authorization`, comments included. That
  covers the test that asserts no `Authorization` header: build the header
  name, e.g. `'Author' + 'ization'`.

    - `libs/ng/auth/src/lib/auth.interceptors.ts` (new): `authInterceptor` and the
      internal `AuthErrorPolicy`. Export `authInterceptor` from `src/index.ts`.
    - `auth.services.ts`: `startLogin` and `clear`, with doc comments.
    - `auth.providers.ts`: the initializer also injects `AuthErrorPolicy`.
    - Specs: `auth.interceptors.spec.ts` (new), plus `auth.services.spec.ts` for
      `startLogin`.
    - `apps/ng-demo/src/app/app.config.ts`: the wiring above.
    - Docs: replace the three "An error-policy interceptor follows" sentences.

  `auth.directives.ts`, `auth.mixins.ts`, all of `libs/ng-bootstrap`, the mock
  interceptor's routes, spec pages other than this brief, and kiln-generated
  files.

## Tests first

Write these first. Each fails to compile before the change, because
`authInterceptor`, `startLogin` and `clear` are missing.

Shared setup for `auth.interceptors.spec.ts`:

- `provideRnForgeAuth()`;
- `provideHttpClient(withInterceptors([authInterceptor]))` and
  `provideHttpClientTesting()`;
- `provideRouter([])`, with a spy on `Router.navigateByUrl`;
- the `FullPageNavigation` stub;
- `sessionStorage.clear()` and `vi.useFakeTimers()` where time matters.

Flush the startup `GET /auth/session` with a signed-in session first. Its tests:

1. A `401` from `GET /auth/session` (call `refresh()`) never navigates.
1. `GET https://other.example/api/x` and `GET /apix` returning `401` and `403`
   reach the caller, and nothing is refetched or navigated.
1. A `401` from `GET /api/orders`:
    - clears credentials;
    - requests `/auth/providers`. Flush one `development` provider and assert
      `assign` is called with `/auth/login/development?return_to=…`. With two
      providers, assert `navigateByUrl` is called with the login page and
      `returnTo` instead;
    - errors the caller with the `401`.
1. Three parallel `401`s from `/api/a`, `/api/b` and `/api/c` cause one
   `/auth/providers` request and one navigation.
1. A `401` from `POST /auth/login/password` (call `loginWithPassword`) reaches
   the form as `PasswordLoginError`, and starts no login.
1. Loop guard:
    - set `sessionStorage['rnf.auth.loginStartedAt']` before creating the
      injector;
    - a `401` from `/api/x` 5 s after startup navigates to
      `/login/error?error=session_not_established` and starts no login;
    - the same test at 11 s starts a login instead.
1. A `403` with body `{ type: 'https://errors.example/csrf-failed' }` on
   `POST /api/x`:
    - triggers one `GET /auth/session`;
    - after setting `document.cookie = 'XSRF-TOKEN=new'`, the retried
      `POST /api/x` carries `X-XSRF-TOKEN: new`;
    - when the retry succeeds, the caller gets the success;
    - when the retry gets a second `csrf-failed`, the caller gets that error and
      there is no third request.
1. Other `403`s:
    - two parallel `403`s with `type` `…/forbidden` on `/api/a` and `/api/b`
      cause one `GET /auth/session`, then `navigateByUrl('/forbidden')`, and
      both callers get their `403`;
    - credentials stay signed in, and `/auth/providers` is never requested.
1. A handled request reaches the backend with no `Authorization` header.

In `auth.services.spec.ts`, add `startLogin`:

- one `oidc` provider → `login`;
- `development` and `password` → the login page;
- `providers()` erroring → the login page.
