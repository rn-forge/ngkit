`ng-demo`'s e2e suite signs in to the
[F4.3](../E4-standard-resource-screen/F4.3-wire-acceptance.md) backend fixture
through its development provider, offline, and exercises the session client end
to end. The fixture grants its fixture accounts different permissions on the
products resource.

## Context

**Depends on:** [F5.2](F5.2-auth-wrapper.md), [F5.3](F5.3-bootstrap-auth-ui.md),
and a released server library, pinned by tag in the fixture's manifest, that
serves the routes in [Design](design.md) with a development provider.

**Entry criterion met (checked 2026-11-14).** Both server libraries the fixtures
pin serve the contract from their current release tags:
`rn-forge-fastapi-v0.4.1` and `rn-forge-django-v0.6.1`. Each was installed in a
throwaway project outside the libraries' own repository, by the same kind of git
pin the fixtures use, for example
`rn-forge-fastapi[transfer] @ git+https://github.com/rn-forge/pykit@rn-forge-fastapi-v0.4.1#subdirectory=packages/rn-forge-fastapi`
(it resolves `rn-forge-auth`, `rn-forge-web` and `rn-forge-commons` from the
same tag). Offline, in debug mode, with the development provider, both answered:

- `GET /auth/session` anonymous: `401` with no `WWW-Authenticate`, and sets
  `XSRF-TOKEN`;
- `GET /auth/providers`:
  `[{ "id": "development", "name": "development", "kind": "development" }]`;
- `GET /auth/login/development?account=<id>&return_to=/products`: `302` to
  `/products`, setting `__Host-session`;
- `GET /auth/session` then: `200` with a camelCase body (`subject`, `provider`,
  `roles`, `permissions`, `authTime`, `amr`, `expiresAt`);
- an unsafe request without `X-XSRF-TOKEN`: `403` `application/problem+json`
  with `type` `<problem type base>csrf-failed`;
- `POST /auth/logout` with the header: `200 {"redirect": null}`, after which
  `/auth/session` is `401`.

The FastAPI check also mounted a products route behind
`requires_permission(caller, "demo.products", …)`: an account holding
`demo.products.list` and `.read` only got `200` on the list and `403` on a
`PATCH`, while an account with `demo.products.update` got `200`.

## Design

Proposed 2026-11-14 from that check (owner decision: the FastAPI fixture is the
primary backend, because the applications built next use FastAPI). S5.4.1
confirms each point with a request before writing the code.

- **FastAPI is the primary backend.** `NG_DEMO_BACKEND` defaults to `fastapi`,
  and CI runs the suite against `apps/ng-demo-api-fastapi`, in place of the
  Django fixture that F4.3 chose for CI. The Django fixture stays as the
  second backend and gets the same auth, so a local run with
  `NG_DEMO_BACKEND=django` still shows that the suite names no backend.
- **Pins.** `apps/ng-demo-api-fastapi` moves from `rn-forge-fastapi-v0.2.0` to
  `rn-forge-fastapi-v0.4.1`, with `rn-forge-sqlalchemy` moved to a tag that
  resolves with it; `apps/ng-demo-api` moves from `rn-forge-django-v0.4.0` to
  `rn-forge-django-v0.6.1`. The F4.3 products suite must still pass on both
  after the bump, and each hand-written piece F4.3 lists stays unless the new
  tag makes it redundant.
- **FastAPI wiring.** `auth_router(config)` and `SessionMiddleware` with
  `sessions_for(config)`; `AuthRoutesConfig` with `problem_type_base` set (it
  is required), `error_route` set to the client's `errorPath`
  (`/login/error`), `trusted_origins` set to `ng-demo`'s dev-server origin,
  and `debug=True`, which allows the in-memory stores. The products routes
  take `requires_permission(caller, "demo.products", <action>)`.
- **Django wiring.** `rn_forge.django.auth` in `INSTALLED_APPS`, the session
  middleware and `CSRF_MIDDLEWARE`, `SESSION_SETTINGS` and `CSRF_SETTINGS`,
  `RN_FORGE_DJANGO["AUTH"]["PROBLEM_TYPE_BASE"]`, the problem-details
  exception handler, and `auth_urlpatterns(config, prefix="auth")` with the
  same `error_route`; the products viewset takes `PermissionKeyPermission`
  with `permission_key = "demo.products"`.
- **Accounts and permissions.** Neither binding is given a database of users.
  Each fixture supplies the three small objects every FastAPI application
  supplies: an `AccountResolver` that accepts the two development accounts, an
  `AuthorizationContextProvider` that returns each account's fixed permission
  set, and an `AccountStateWriter` that keeps state in memory. The Django
  fixture reuses the same objects instead of Django's group-derived keys, so
  the keys stay the ones `ng-demo` already checks (`demo.products.<action>`)
  and neither the screen nor the mock changes. Import and template download
  need the `upload` action.
- **Proxy.** `proxy.fixture.json` sends `/auth` to the fixture as well as
  `/api`.
- **Browsers.** The session cookie is `__Host-` and `Secure`, which browsers
  accept on `http://localhost` only where they treat it as a secure context.
  S5.4.1 records which Playwright projects run against the fixture; one that
  refuses the cookie is excluded there, with the reason, rather than served
  over HTTPS.

## S5.4.1 — Fixture auth

**State:** Closed (2026-11-16)

**Acceptance:** the backend fixture serves the auth routes through the pinned
library, with a development provider and two fixture accounts: one with every
`demo.products.*` permission and one with `demo.products.list` and
`demo.products.read` only, on both fixtures. Unsafe requests without the XSRF
header are refused with the `csrf-failed` problem, and the F4.3 products suite
still passes on both.

**Outcome:** the accounts are `demo-admin` and `demo-reader`; the suite runs on
Chromium and Firefox, and WebKit is excluded because it does not store the
`__Host-session` cookie on `http://localhost`.

## S5.4.2 — Acceptance run

**State:** New

**Acceptance:** with `ng-demo` served against the fixture, the e2e suite shows:

- an anonymous visit to the products screen goes through the development
  provider (signing in with `?account=`) and returns to the products screen;
- the read-only account sees no create, edit or delete actions, and a direct
  `PATCH` it makes is answered `403` and lands on the forbidden page while
  still signed in;
- after the fixture ends the session, the next request starts a login, and a
  session cookie the browser never stores ends at the error page
  (`/login/error`) with `session_not_established` instead of looping;
- logout returns to the login page and `/auth/session` then answers `401`.

## Acceptance

- Each story's acceptance holds (S5.4.1, S5.4.2).
- `pnpm nx e2e ng-demo-e2e` passes on both CI paths against the FastAPI fixture,
  and locally with `NG_DEMO_BACKEND=django`.
- An optional CI job runs the same suite through a local Keycloak container as
  an OIDC provider; it is not required for the feature to be done.
