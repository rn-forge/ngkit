# F6.1 — `loadingTimings`

**Status:** elaborating · **Owner:** ngkit · **Epic:** [E6](index.md)

**Depends on:** none.

## Design

```ts
export interface LoadingTimings {
  /** ms of loading before `show` turns true. */
  readonly delay: number; // 300
  /** ms of loading before `slow` turns true. */
  readonly slow: number; // 1000
  /** ms of loading before `stalled` turns true. */
  readonly stalled: number; // 10000
}
export interface LoadingState {
  /** True once the current load has lasted `delay`; a load that ends sooner never shows. */
  readonly show: Signal<boolean>;
  readonly slow: Signal<boolean>;
  readonly stalled: Signal<boolean>;
}
/** Application-wide defaults; provide it to change them. */
export const RNF_LOADING_TIMINGS: InjectionToken<LoadingTimings>;
export function loadingTimings(
  loading: Signal<boolean>,
  options?: Partial<LoadingTimings> & { readonly injector?: Injector },
): LoadingState;

// usage
readonly orders = httpResource(() => `/v1/orders?${this.query()}`);
readonly timing = loadingTimings(this.orders.isLoading);
// @if (timing.show()) { <skeleton /> } @if (timing.stalled()) { <p>Still working…</p> }
```

`loadingTimings` runs in an injection context, or takes `injector`. It reads only the boolean, so it works with `Resource.isLoading`, `CrudList.loading` or any other loading signal, and it knows nothing about HTTP and shows no text. Per-call options override `RNF_LOADING_TIMINGS`, whose factory returns the defaults above.

A load starts when `loading` turns true and ends when it turns false. A `reload()`, or a changed request, that keeps `loading` true does not restart the clock; one that turns it false and then true does.

## Stories

### S6.1.1 — The signals and their timers

**Status:** elaborating

**Acceptance:**

- With fake timers (`vi.useFakeTimers()`, no real sleeps): `show`, `slow` and `stalled` are `false` while `loading` is `false`; each turns `true` at its threshold while `loading` stays `true`, and not one tick earlier.
- A load that ends before `delay` never sets `show`; a load that ends after a threshold resets all three to `false` at once.
- A second load after the first ended starts from zero: no leftover `slow` or `stalled` from the first.
- When `loading` turns `false`, or the injector is destroyed, every pending timer is cleared; advancing the clock afterwards changes no signal.
- Per-call options override `RNF_LOADING_TIMINGS`, and a provided `RNF_LOADING_TIMINGS` overrides the defaults.
- Timings that are not `0 <= delay <= slow <= stalled` throw an `Error` prefixed `[rn-forge.ng.core]` that names the out-of-order values.
- `loadingTimings`, `LoadingTimings`, `LoadingState` and `RNF_LOADING_TIMINGS` are exported from `@rn-forge/ng/core`. The doc comment names ADR-0001 exemption 3 and the npm check in [E6's Design](index.md#design).

### S6.1.2 — Behaviour over a resource

**Status:** elaborating

**Acceptance:**

- With `provideHttpClientTesting` and `HttpTestingController`, over `httpResource(...).isLoading`: a request flushed before `delay` never sets `show`; a request left pending past each threshold sets each signal; flushing it resets all three.
- An error response resets all three, as a success does.
- Changing the request while one is pending (the first is cancelled, the second issued) keeps the clock running from the first request's start.
- Over `createCrudList()`'s `loading`, with a fake data source: moving to the next page with a slow `list` sets `show` after `delay`.

## Open questions

- **A minimum display time?** Once `show` is true, a load that ends 20 ms later still flashes the skeleton for 20 ms. `ngxtension`'s `derive-loading` and `spin-delay` hold the flag for a minimum time (`minDuration`, around 200 to 500 ms) to avoid that. Adding a `minDuration` option means `show` can stay true after `loading` is false. Recommendation: add it, defaulting to 0 so the default behaviour is the one above.
