# S6.1.2 — Behaviour over a resource

Brief for [S6.1.2](../F6.1-loading-timings.md#s612-behaviour-over-a-resource),
at `508e700`.

## Goal

Prove that `loadingTimings` behaves as specified over the two real loading
signals it is meant for: `httpResource().isLoading` and `createCrudList()`'s
`loading`. The story adds tests only; the code under test already exists.

## Settled

- `loadingTimings` reads only a `Signal<boolean>` and knows nothing about HTTP
  (F6.1 Design). Over a resource, a changed request or `reload()` that keeps
  `isLoading` true does not restart the clock; one that turns it false and
  then true does (F6.1 Design).
- S6.1.1 is Closed; its behaviour and `minDuration` default of 0 are settled
  (owner decision, 2026-11-18). This story does not change them.
- `@rn-forge/ng/crud` already imports `@rn-forge/ng/core`
  (`libs/ng/crud/src/lib/crud.errors.ts:3`, `crud.types.ts:2`); `core` must
  never import `crud`. So the `createCrudList` test lives in the crud entry
  and imports `loadingTimings` from `@rn-forge/ng/core`; the `httpResource`
  test lives in core. `@nx/enforce-module-boundaries` allows both directions
  of tags (`*`), so the rule is the dependency direction, not a lint
  constraint.
- Tests use fake timers (`vi.useFakeTimers()`), no real sleeps, and
  `TestBed.tick()` to run effects (the existing specs are zoneless in style).

## Current behaviour

- `libs/ng/core/src/lib/core.loading.ts:70-163`:
  `loadingTimings(loading, options)`. An `effect` (`:145-156`) reads
  `loading()`; on a change of the boolean it calls `start()` (`:114-125`, arms
  `show`, `slow`, `stalled` timers) or `end()` (`:127-138`, clears timers,
  resets `slow` and `stalled`, resets `show` unless held by `minDuration`). A
  repeat of the same value is ignored (`:149`), which is why a request change
  that keeps `loading` true does not restart the clock.
- `libs/ng/crud/src/lib/crud.list.ts:90-99`: `rxResource` with `params` of page
  size, token, order and filter and `stream` calling `dataSource.list`; `:128`
  exposes `loading: resource.isLoading`. `next()` (`:139`) changes the token,
  which makes the resource load the next page.
- Existing tests: `libs/ng/core/src/lib/core.loading.spec.ts` (331 lines; a
  top-level `describe('loadingTimings')` with `vi.useFakeTimers()` in
  `beforeEach`, `TestBed.tick()` after each `loading.set`);
  `libs/ng/crud/src/lib/crud.list.spec.ts` (fake source returning `of(...)`,
  `settle()` = `TestBed.tick(); await Promise.resolve(); TestBed.tick()`);
  `libs/ng/crud/src/lib/crud.standard.spec.ts:1-25` (`provideHttpClient()` +
  `provideHttpClientTesting()` + `HttpTestingController`).

Observed with throw-away prototype specs at `508e700` (deleted; the tree is
clean), each with fake timers, `TestBed.inject(Injector)` passed as `injector`,
and `settle()` as above. Every acceptance bullet already passes; no change to
`core.loading.ts` is needed and no assumption about Angular is wrong.

| Bullet | Observed |
| -- | -- |
| `httpResource` request flushed before `delay` | `isLoading()` is true after the first `settle()`; flushing at 299 ms and advancing 5 s leaves `show`, `slow`, `stalled` all `false`. |
| Request pending past each threshold, then flushed | (`show`, `slow`, `stalled`) is (true, false, false) at 300 ms, (true, true, false) at 1000 ms, (true, true, true) at 10000 ms; after `flush({})` and `settle()` all three are false. |
| Error response | Same trace as above; after `flush('x', { status: 500, statusText: 'E' })` and `settle()` all three are false. |
| Request changed while one is pending | After 200 ms, setting the request signal and `settle()` leaves `isLoading()` true and all three false; the first request is cancelled (`TestRequest.cancelled` true), the second is open. At 300 ms from the first start `show` is true; at 1000 ms `slow` is true. Flushing the second resets all three. |
| `createCrudList` `loading`, `next()` with a slow `list` | Initial load with `of(...)` leaves all false (after 5 s idle too). With `list` returning a never-completing `Subject`, `next()` then `settle()` gives `loading()` true and `show` false; `show` is false at 299 ms and true at 300 ms; `slow` true at 1000 ms; `next` emitting then `settle()` gives `loading()` false and all three false. |

Gotchas found: do not call `TestBed.configureTestingModule` after the first
`TestBed.inject` in the same test (it throws), so configure in `beforeEach`; and
`vitest` runs these specs in a bundled browser-like environment, so a scratch
spec cannot import `node:fs` or print with `console.log` reliably.

## Tests first

These are characterization tests over code that already works, so none fails
before the change; they pass as soon as they are written. To show each can fail,
the implementer temporarily changes `delay` in the test from 300 to 301 (or the
threshold assertion by one tick), sees the test fail, and reverts; note that in
`## Result`. If any test fails for real, stop and record the output in
`## Result` instead of changing `core.loading.ts`.

Helpers for the httpResource describe: `beforeEach` calls `vi.useFakeTimers()`
and
`TestBed.configureTestingModule({ providers: [provideHttpClient(), provideHttpClientTesting()] })`;
`afterEach` calls `vi.useRealTimers()` and
`TestBed.inject(HttpTestingController).verify()`. A `start(url: () => string)`
helper builds `httpResource(url, { injector })` and
`loadingTimings(resource.isLoading, { injector })` with
`injector = TestBed.inject(Injector)` and returns both plus the controller. A
`settle()` helper does
`TestBed.tick(); await Promise.resolve(); TestBed.tick()`.

In `libs/ng/core/src/lib/core.loading.spec.ts`,
`describe('loadingTimings over httpResource')`:

1. `it('never shows a request flushed before delay')`: start `/a`, `settle()`,
   advance 299 ms, `expectOne('/a').flush({})`, `settle()`, advance 5000 ms;
   `show`, `slow`, `stalled` are all `false`.
1. `it('sets each signal at its threshold and resets all on flush')`: start
   `/a`, `settle()`, take `expectOne('/a')`. At 299 ms `show` is `false`; at
   300 ms `show` is `true` and `slow` `false`; at 999 ms `slow` is `false`; at
   1000 ms `slow` is `true` and `stalled` `false`; at 9999 ms `stalled` is
   `false`; at 10000 ms all three are `true`. Then `flush({})`, `settle()`:
   all three `false`.
1. `it('resets all three on an error response')`: as test 2 up to 10000 ms, then
   `flush('x', { status: 500, statusText: 'Server Error' })`, `settle()`: all
   three `false`.
1. `it('keeps the clock running when the request changes while pending')`: a
   `signal('a')` drives the URL (`/r` + value). Start, `settle()`, advance 200
   ms, set the signal to `'b'`, `settle()`. Assert the resource's
   `isLoading()` is `true` and all three are `false`. `http.match(() => true)`
   returns two requests: the first with `cancelled` true, the second not.
   Advance 99 ms: `show` still `false`; advance 1 ms (300 ms from the first
   start): `show` is `true`; advance 700 ms (1000 ms from the first start):
   `slow` is `true`. Flush the second request, `settle()`: all three `false`.

In `libs/ng/crud/src/lib/crud.list.spec.ts`,
`describe('createCrudList loading timings')`:

5. `it('shows after delay while the next page is slow')`: a source whose `list`
   returns `of({ items: [{ id: 1 }], nextPageToken: 't2' })` for the first
   request and a `Subject` for the second. `vi.useFakeTimers()` in the test
   (restore in `afterEach`). `const injector = TestBed.inject(Injector)`;
   `list = createCrudList(source, { injector })`;
   `timing = loadingTimings(list.loading, { injector })`. After `settle()` the
   first page is loaded and all three are `false`; advance 5000 ms, still
   `false`. `list.next()`, `settle()`: `list.loading()` is `true`,
   `timing.show()` is `false`; advance 299 ms: `false`; advance 1 ms: `true`.
   Advance 700 ms: `timing.slow()` is `true`. Emit the second page on the
   `Subject`, `settle()`: `list.loading()` is `false`, all three `false`, and
   `list.items()` is the second page.
